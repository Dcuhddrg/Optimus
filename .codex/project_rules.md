# Codex Project Rules

> 本文件是 Codex 在当前仓库中的工作约束。处理任务前应先阅读，并以此作为默认行为边界。

---

## 🔴 BOUNDARIES — 绝对禁止

在没有明确指令的情况下，Codex **绝对禁止**：

- **重构未涉及的文件**：只修改任务明确涉及的文件
- **更改技术选型**：不替换当前使用的库、框架或工具
- **删除注释或 TODO**：注释和 TODO 视为团队知识，不擅自删除
- **自动升级依赖版本**：依赖变更必须有明确任务要求
- **修改环境配置文件**：`.env`、`.env.example`、部署配置等非必要不触碰
- **跨越模块边界**：后端任务不顺手改前端占位内容，文档任务不顺手改业务代码
- **顺手扩展需求**：只完成用户明确要求的范围

出现以下情况时必须暂停并说明：

- 需要触碰上述禁止项
- 任务描述与仓库现状明显冲突
- 发现严重问题但不在当前任务范围
- 不确定应该修改哪个模块

## 🏗️ CONTEXT — 当前仓库现状

### 项目结构

```text
project-root/
├── server/                 # 当前主要开发面：Go 后端骨架
│   ├── main.go             # 唯一程序入口
│   ├── config/             # 配置结构与默认配置
│   ├── core/               # 配置、日志、HTTP 服务启动
│   ├── global/             # 全局共享对象
│   ├── initialize/         # 基础设施与路由装配
│   ├── router/             # 路由分组与注册
│   ├── api/v1/system/      # HTTP handlers
│   ├── service/system/     # 业务响应封装
│   ├── middleware/         # 日志、恢复、JWT/Casbin 占位中间件
│   ├── model/common/       # 公共响应模型
│   └── utils/              # 轻量工具与 claims
├── web/                    # 前端占位目录，当前不是主要交付面
├── docs/superpowers/       # 设计与实施计划文档
└── .codex/                 # Codex 本地规则与辅助文件
```

### 当前架构

- 当前主线是 `server/` 下的 Go 后端骨架，不是完整业务系统
- `server/main.go` 只负责初始化和启动，不承载业务逻辑
- 默认分层流向为：`router -> api -> service`
- 基础设施装配统一放在 `initialize/`
- 运行时核心能力放在 `core/`
- 全局共享实例放在 `global/`
- 当前公共接口为：
  - `GET /api/v1/health`
  - `GET /api/v1/ping`
  - `GET /api/v1/base/ping`

### 当前技术栈

| 层 | 技术 |
|----|------|
| 语言 | Go 1.23 |
| HTTP 框架 | Gin 1.10 |
| ORM | GORM 1.25 |
| 数据库目标 | MySQL |
| 配置 | Viper 1.19 |
| 日志 | Zap 1.27 |
| Redis 客户端 | go-redis/v9 |
| 权限 | Casbin v2 |
| JWT | github.com/golang-jwt/jwt/v5 |
| 测试 | Go test + testify |

### 关键约定

- 配置文件使用 `server/config.yaml`
- 环境变量覆盖使用 `OPTIMUS_` 前缀
- Redis 和 Casbin 在启动时保持可选
- 当前前端 `web/` 目录不是主要实现面，未明确要求时不要扩展前端内容

## 📐 CONVENTIONS — 编码与修改约定

### Go 代码

- 优先复用现有目录边界，不额外发明新层次
- 入口文件保持薄，不在 `main.go` 写业务逻辑
- 路由注册留在 `router/`，不要把 handler 内联回 `initialize/`
- 业务逻辑进入 `service/`，不要直接堆在 router 中
- 基础设施初始化进入 `initialize/`
- 共用响应结构放 `model/common`
- 轻量工具放 `utils/`，不要把不相关逻辑塞成“大工具箱”

### 注释与命名

- **对话交流**：中文
- **代码标识符**：英文
- **代码注释**：中文优先，简洁说明意图
- **Git commit**：遵循仓库已有约定；如果提交，优先使用中文描述

### 依赖与范围

- 不因为“顺手需要”就升级依赖
- 不为了美化结构重排无关文件
- 不补超出当前任务范围的大量测试
- 如需新增依赖，必须与当前任务直接相关

## 📤 FORMAT — 面向 Codex 的输出要求

### 工作方式

1. 先用一句话复述任务范围
2. 明确将修改的文件边界
3. 如无歧义，直接执行，不做多余延伸
4. 完成后用简明结构汇报结果

### 结果汇报默认格式

```text
## 变更说明
[1-2 句话说明改了什么]

## 影响范围
- 修改文件：[列出变更文件]
- 影响功能：[说明影响点]
- 未修改：[说明明确没动的相关区域]

## 注意事项
[仅列出需要人工关注的点；没有则写“无”]
```

### 禁止的输出习惯

- 不说“顺便优化了”
- 不在未被要求时给出大段替代方案
- 不把无关问题混进当前交付
- 发现潜在问题时，先完成当前任务，再在“注意事项”中简述

## 🔄 VERIFICATION — 验证基线

后端相关改动默认应满足：

- 在 `server/` 下执行 `go test ./...` 通过
- 在 `server/` 下执行 `go build ./...` 通过

如果任务涉及启动或路由行为，额外验证：

- 服务能正常启动
- `/api/v1/health` 保持可用
- 若涉及 ping 路由，相关接口返回预期 JSON

## 📝 PROJECT NOTES — 当前已知事实

- 当前仓库以 Go 后端骨架为主，不要套用通用 React/Node 模板规则
- `web/` 目录当前只是占位，不应假设已有 React/Tailwind/Playwright 体系
- 现阶段重点是保持骨架清晰、可运行、可测试，不提前扩展完整业务域
