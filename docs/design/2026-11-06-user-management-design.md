# 用户管理设计

- 状态：已批准（用户逐条确认，2026-11-06）；实现状态：3.1、3.4 实现中（[#80](https://github.com/Dcuhddrg/Optimus/issues/80) 第一个 PR），其余未开始。
- 关联：[#80](https://github.com/Dcuhddrg/Optimus/issues/80)（实施与验收）、[#4](https://github.com/Dcuhddrg/Optimus/issues/4)（审批流，以本设计为前置）、[ADR-005](../adr/0005-ldap-identity-optimus-authorization.md)（身份与授权分工）。
- 对照基线：gin-vue-admin 本地仓库 `67894b11`（比文档其他处引用的 `cee04b08` 新）。

## 1. 背景

审批流需要按"审批角色 + 项目负责人"确定审批人。核查现状时发现：

- LDAP 用户首次登录才在 Optimus 建账号（`service/system/auth.go` 的 `syncLDAPUser`），管理员无法在此之前分配角色。
- 用户状态只在登录时检查（`auth.go` 的 `Login`、`loginLDAP`）。JWT 中间件不查状态，token 临期续期时原样复制旧 claims（`middleware/jwt.go`）。
- 角色 ID 写在 token 里（`utils/claims.go` 的 `RoleIDs`），Casbin 直接用它判断（`middleware/casbin_rbac.go`）。停用用户、摘除角色、停用角色，对一直在线的用户都不生效。
- 角色的启用/停用状态（`SystemRole.Status`）是 Optimus 独有的，GVA 的 `SysAuthority` 没有这个字段。
- 测试环境的 OpenLDAP（容器 `optimus-test-openldap`，`dc=optimus,dc=test`）在 `ou=people` 下有 10 个用户，分 qa、dev、ops、sales、manger 5 个 `departmentNumber`，没有组，也没有 `manager` 属性。`ou=robots` 下是绑定用的机器人账号。

## 2. 原则

LDAP 只负责身份：认证，以及用户资料的同步。角色、审批资格、项目成员这些授权全部在 Optimus 里维护，不做 LDAP 组到角色的映射。理由和代价见 [ADR-005](../adr/0005-ldap-identity-optimus-authorization.md)。

本地账号只保留内置的 `admin`，用于 LDAP 不可用时的应急登录。

## 3. 当前阶段

### 3.1 权限即时生效（D1）

**规则**

- 用户停用、用户角色增减、角色删除、角色权限修改，都在下一个请求生效。
- 已停用用户的请求返回 HTTP 401，`msg` 为"账号已停用"。前端跳回登录页并显示这句话。
- 登录接口对已停用账号仍然返回 code 7 和"账号已停用"，与现在一致：登录接口本身不需要认证，"不允许登录"是这次请求的业务结果。
- 用户的角色被摘光时不会被踢下线，只是失去权限，访问页面时看到 ForbiddenPage。这是权限变化，不是身份失效。

**实现**

- JWT 中间件解析 token 后，按用户 ID 取出用户的当前状态和角色 ID，写入请求上下文。Casbin 中间件改用这份角色，不再读 token 里的 `RoleIDs`。token 里仍保留 `RoleIDs`，只给前端展示用。
- 取数结果放在进程内缓存里，键是用户 ID。缓存的内容就是加载权限时读的全部字段：状态、角色 ID、人员类型、有效期、对接人。
- **失效规则**：凡是改动上述字段、角色审批标记或角色接口权限的写入，都必须在提交后让对应缓存失效，再返回。写入路径一一列出，新增写入路径时也要加进这张表：

  | 写入路径 | 可能改变 | 失效范围 |
  | --- | --- | --- |
  | 管理员修改用户状态 | 状态 | 该用户 |
  | 管理员增减用户角色 | 角色 | 该用户 |
  | 管理员设置、修改或清空第三方的有效期、对接人 | 有效期、对接人 | 该用户 |
  | LDAP 登录时同步本人资料（含首次登录建账号） | 人员类型（员工 ↔ 第三方）、默认角色 | 该用户；资料没有变化时可以跳过 |
  | 同步执行接口（新增、更新、停用） | 人员类型、状态、角色 | 全部 |
  | 删除角色、修改角色接口权限 | 角色、Casbin 策略 | 全部，并重新加载 Casbin（见下） |
  | 修改角色的审批标记 | 第三方的有效角色（第三方持有的审批角色会被忽略） | 全部 |
  | 迁移 | 角色绑定 | 服务启动、开始接收请求之前就执行完，无需失效 |

  这几种情况不需要失效：到期是每个请求拿缓存里的 `ExpiresAt` 和当前时间比较，时间一到自然生效；对接人被停用或到期只做标记，不影响第三方的权限（见 3.6）。
- 修改接口按固定顺序执行：提交事务 →（涉及接口权限时）重新加载 Casbin → 版本号加 1 并清缓存 → 返回成功。
- 防止旧值回填：缓存带一个全局版本号，每次清缓存都把它加 1。请求加载权限前记下当前版本号，写入缓存时如果版本号已经变了，就丢弃本次结果，不写入。否则会出现这样的交错：请求 A 读到旧角色后暂停，管理员撤权并清缓存，A 再把旧角色写回缓存，后续请求就一直沿用旧权限。权限变更很少发生，一个全局版本号就够用。
- **版本检查和写入必须与清缓存互斥**：缓存用一把互斥锁保护。"比较版本号并写入"在锁内一步完成；"版本号加 1 并清缓存"也在同一把锁内完成。只比较版本号而不加锁不够，还会出现这样的交错：A 比较时版本号没变，随后暂停；撤权请求加版本、清缓存并返回；A 恢复后把旧值写进去。加锁后，两件事只能先后发生：A 先写入，就会被随后的清缓存清掉；清缓存先发生，A 比较时就会发现版本号变了。从数据库加载权限的步骤不在锁内，锁只覆盖内存里的比较和赋值，持锁时间是微秒级。读缓存可以用读锁。
- **Casbin 策略同步**：清用户缓存只能让请求重新取到角色 ID，接口是否放行由进程内的 Casbin enforcer 判断，它保存着策略的内存副本。因此：
  - 修改角色接口权限、删除角色时，事务提交后调用 `FreshCasbin()` 从 `casbin_rule` 重新加载全部策略，然后才加版本、清缓存、返回。现有的 `UpdateRolePermissions` 已经是这个顺序；删除角色也要照做。
  - **重载串行**：所有重载（修改接口触发的、后台重试的、启动时的）共用一把重载锁，拿到锁之后才读数据库，读完换上新策略再放锁。这样后完成的重载一定读到更晚提交的数据，不会出现"先开始的重载后完成，把旧策略换回来"。换策略的方式是先在新的 enforcer 里加载完整策略，成功后原子替换当前 enforcer；加载失败时不动当前 enforcer。
  - 关闭 `SyncedCachedEnforcer` 的判定结果缓存（`EnableCache(false)`）。这层缓存和用户缓存有同样的回写问题：一次判定没命中缓存，用旧策略算出结果，此时 `LoadPolicy` 清空了判定缓存、换上新策略，这次判定再把旧结果写进去，会按 `SetExpireTime` 保留 1 小时。Casbin 在内存里按角色、路径、方法匹配，开销很小，不需要这层缓存。
  - **重载失败时拒绝放行（fail-closed）**：数据库已经是新策略、内存还是旧策略时，旧策略可能放行已撤掉的权限，所以不能继续用它鉴权。
    - 重载失败后，进入"策略待同步"状态。此状态下 Casbin 中间件拒绝所有需要接口权限的请求，返回 code 7"权限系统同步中，请稍后重试"，不调用旧策略。登录、获取当前用户信息这类不经过 Casbin 的接口不受影响。
    - 后台按递增间隔自动重试（1 秒起，最长 30 秒），在重载锁内重读数据库，成功后清除"策略待同步"状态，再加版本、清用户缓存，记一条恢复日志。不依赖管理员重试。
    - 触发重载的修改接口返回 code 7"权限已保存，正在重新加载，请稍后确认"，并记错误日志。不回滚数据库，因为数据库里的策略本身是对的。
    - 重载失败基本只在数据库不可用时发生，这时系统本来就无法正常工作，拒绝请求不会额外损失什么。
    - 服务启动时的首次加载失败，同样进入"策略待同步"并后台重试。现在 `GetCasbin` 用 `sync.Once` 初始化，失败后永远返回 nil，Casbin 中间件对 nil 调用 `Enforce` 会 panic，实现时一并修掉。
- 生效时刻是**修改接口返回成功的那一刻**。管理员看到"成功"之后才开始加载权限的请求，一定使用新权限。从事务提交到接口返回之间只有几毫秒，这段时间内的请求视为和这次修改同时发生，允许使用旧权限；已经开始执行的请求，也允许按旧权限执行完。要消除这段窗口，就得让每个请求在整个处理过程中都持有读锁，修改期间所有请求都要排队，所以不这样做。这和下面缓存写入用的互斥锁是两回事：那把锁只包住内存里的比较和赋值。
- LDAP 同步的执行接口遵循同一规则：等所有已处理的人都提交完、缓存也清完，才返回结果，部分完成时也一样。迁移在服务启动、开始接收请求之前就执行完了，不存在这个问题。
- 测试覆盖以下交错，暂停点用测试专用的钩子注入：
  - 修改接口返回之后，后续请求一律按新权限判断；
  - 加载权限的请求在读完数据库、写缓存之前暂停，管理员在此期间完成修改，这个请求取到的旧结果不能写回缓存；
  - 加载权限的请求在锁内比较完版本号、赋值之前暂停：撤权请求的清缓存要等它写完才能执行，撤权接口返回后缓存里没有旧值，下一个请求使用新权限；
  - 修改角色接口权限后，下一个请求按新策略放行或拒绝；Casbin 判定缓存已关闭，并发判定不会留下旧结果。
- 当前是单实例部署，也没有 Redis 消费者（见 [#55](https://github.com/Dcuhddrg/Optimus/issues/55)），进程内缓存就够用。以后改成多实例时，需要换成共享缓存或广播失效。
- token 不加入黑名单。用户重新启用后，未过期的 token 可以继续使用。
- 菜单权限码是前端在登录或获取当前用户信息时拿到的。接口权限即时生效，菜单要等页面刷新后才更新；在此期间点到已经无权访问的页面，会被接口拒绝。

**与 GVA 的差异**

GVA 的 `middleware/jwt.go` 里有"已登录用户被禁用就让 token 失效"的检查，但被注释掉了，注释写着性能考虑、需要时自行打开。GVA 给用户切换角色时，也只给操作者本人重新签发 token。Optimus 把检查默认打开，用缓存控制开销，因为"权限在 Optimus 管控"要求改动马上生效。

### 3.2 角色去掉状态，新增删除

照 GVA 处理：

- 去掉 `SystemRole.Status`、`UpdateRoleStatus` 接口、前端角色页上的启用/停用开关。`queryUserRoles` 不再按 `roles.status` 过滤。
- 迁移：先解除所有已停用角色上的用户绑定，再删除状态字段。每解除一条绑定记一条审计，处理了哪些角色、涉及哪些用户写进迁移日志。迁移前后，每个用户实际拥有的权限不变：角色本身保留，只是不再有人持有。不能因为当前环境只有 `admin`、`user` 两个角色、且都处于启用状态，就省掉这一步。
- 新增删除角色接口，参照 GVA 的 `DeleteAuthority`：
  - 受保护的角色不能删，包括 `admin` 和默认角色 `user`。新建 LDAP 用户时要绑定 `user`，启动时由种子数据保证它存在。
  - 还有用户使用的角色不能删，提示先移除这些用户。
  - 被审批链配置引用的审批角色不能删。这一条的检查在审批流实现时补上。
  - 删除时一起清掉 `sys_role_permissions` 里的关联和 Casbin 规则，然后清空权限缓存，并记审计日志。

### 3.3 从 LDAP 同步用户（D2 至 D6）

**触发（D2）**

- 用户管理页提供"从 LDAP 同步"按钮，由管理员手动触发全量同步。
- 登录时同步本人资料的逻辑保留。
- 定时同步以后再做，见第 4 节。

**范围（D3）**

- 用现有的 base DN 和登录过滤条件推导同步范围，同步范围和能登录的范围因此是同一批人。
- 只把 `{username}` 换成 `*` 不可靠：`(&(uid={username})(!(cn={username})))` 会变成 `(!(cn=*))`，`(|(uid={username})(mail={username}))` 的范围也会变。所以限制登录过滤条件的写法，保存配置时用 LDAP 过滤器解析器解析并校验：
  - `{username}` 只出现一次，并且形式是 `(<username_attr>={username})`，属性必须是配置里的用户名属性。
  - 这一项要么就是整个过滤条件，要么是最外层"与"（`&`）的直接子项。旁边可以加任意不含 `{username}` 的条件，例如 `(&(uid={username})(memberOf=cn=ops,ou=groups,dc=optimus,dc=test)(!(employeeType=disabled)))`。
  - `{username}` 出现在否定（`!`）、或（`|`）、子串匹配、嵌套的"与"里，或者出现多次，都拒绝保存，提示允许的写法。因此"用户名或邮箱都能登录"的写法不再支持；当前配置是 `(uid={username})`，不受影响。
  - 同步过滤条件 = 把这一项换成存在性条件 `(<username_attr>=*)`，其余条件原样保留。这是一个过滤器结构，不是字符串替换，`*` 不会被转义。
- 登录时仍然把 `{username}` 替换成转义后的用户名，与现在一致。
- 用 LDAP 分页查询（paged results）取全部结果，不受服务端单次返回数量的限制。
- 以下四类条目视为"无法识别身份"：缺少用户名属性；缺少目录标识属性；在同步范围内和其他条目的用户名相同；在同步范围内和其他条目的目录标识相同。OpenLDAP 默认不保证 `uid` 唯一，只有开启 `slapo-unique` 才会保证，测试环境没有开启。这类条目不会被新增或更新，处理方式见 D6。

**字段（D4）**

| 字段 | LDAP 属性配置 | 说明 |
| --- | --- | --- |
| 目录标识 | `id_attr`（新增，从白名单选择，默认 `entryUUID`） | 新增 `SystemUser.ExternalID`；不可变，用作匹配身份的键 |
| 用户名 | `username_attr`（现为 `uid`） | 登录名；目录里改名时随之更新 |
| 显示名 | `display_name_attr`（现为 `cn`） | 已有 |
| 邮箱 | `email_attr`（现为 `mail`） | 已有 |
| 部门 | `department_attr`（新增，默认 `departmentNumber`，留空表示不同步） | 新增 `SystemUser.Department`；只用于展示和筛选，不参与授权 |
| 人员类型 | `employee_type_attr`（新增，默认 `employeeType`）；第三方取值列表 `external_type_values`（新增，默认 `contractor`） | 新增 `SystemUser.PersonType`（`employee` 或 `external`），规则见 3.6 |

**身份匹配**

- 登录和同步都按 `ExternalID` 匹配 Optimus 账号，不按用户名匹配。uid 可能被另一个人复用，例如员工 A 离职后，同一个 uid 分给了员工 B。如果按用户名匹配，B 会接手 A 的账号、角色和项目关系；要是复用发生在两次同步之间，A 的账号甚至从来没被停用过。
- `id_attr` 只能从白名单里选，不能随意填写：`entryUUID`（OpenLDAP）、`nsUniqueId`（389-DS）、`ipaUniqueID`（FreeIPA）。这几个属性都由目录服务器自动生成，并保证唯一。这样可以避免误配成某个多人共用的属性，否则两个 LDAP 用户会对上同一个 Optimus 账号，后登录的人会被当成前一个人改了名，并继承他的权限。`entryUUID` 是操作属性，查询时必须显式列出才会返回。AD 的 `objectGUID` 是二进制值，等以后接入 AD 时再加入白名单。
- 只要有账号已经绑定了 `ExternalID`，就不允许修改 `id_attr`。保存配置时拒绝，提示"已有 N 个账号绑定了目录标识，不能切换标识属性"。否则系统会拿旧属性的值去查新属性，登录和确认缺席都会出错。需要切换时，要用专门的标识迁移工具，见第 4 节。
- 除了白名单，还要检测重复标识，作为第二道防线：
  - 同步时，两个条目的标识相同，两个都归为"无法识别"。
  - 登录时读到标识后，再用 `(<id_attr>=<值>)` 在 base DN 下查一次，结果不是正好 1 条，就拒绝登录，提示"目录身份信息异常，请联系管理员"，并记审计。这会让每次登录多一次查询。
- 用户名改了、`ExternalID` 没变：视为同一个人改名，更新用户名，角色和项目都保留。
- 用户名一样、`ExternalID` 不一样：视为另一个人，记为冲突。
  - 登录时拒绝，提示"账号冲突，请联系管理员"，并记审计。
  - 同步预览中把它列为"冲突"，执行同步时不自动处理。
  - 管理员确认"这是另一个人"之后，旧账号被停用，改名为 `<uid>~<旧账号 ID>` 后保留，UUID 不变，旧的角色、项目和审计引用都不变；新人另建一个账号，不继承旧账号的任何东西，默认角色按新条目的人员类型决定：员工绑定 `user`，第三方不绑定任何角色（见 3.6）。整个过程记审计。
- 登录时如果读不到有效的目录标识，就拒绝登录，提示"目录身份信息缺失，请联系管理员"，并记审计。这条对所有账号都适用。
- 登录时如果目录里有同名条目，现在的做法是查询上限设为 1（`utils/ldap/ldap.go`），超出就报错，登录失败。改为单独识别这种情况，提示"目录中存在同名账号，请联系管理员"，并记审计，不再和密码错误显示成同一种失败。
- LDAP 配置页的"测试连接"，在同步范围内抽样读取 `id_attr`。读不到时提示"读不到目录标识，请检查属性名或绑定账号的读权限"。保存配置时不拦截，但要提示：问题修好之前，LDAP 用户都无法登录。
- 现有的"测试连接"有缺陷，主干上已存在，实现时一并修复（[ldap.go](../../server/utils/ldap/ldap.go)）：
  - 它把 `*` 传给会转义用户名的 `replaceLDAPUsername`，默认过滤条件实际变成 `(uid=\2a)`，查的是 uid 字面等于星号的条目。改为使用上面推导出的同步过滤条件。
  - 查到 0 条时只检查有没有报错，照样报告成功。改为至少查到 1 条才算通过，否则提示"同步范围内没有用户，请检查 base DN 和过滤条件"。
  - 查询上限是 1，修好过滤条件后多条匹配会返回"超出数量限制"。测试连接把这个结果当作正常，取返回的条目做抽样。
- 账号 UUID：新建账号（LDAP 用户，以及以后的本地账号）一律使用随机 UUID（`google/uuid` v4，与 GVA 相同），不再用 `ldap:<用户名>` 拼出来，也不直接拿 `ExternalID` 当 UUID。UUID 是 Optimus 自己的账号标识，以后目录迁移导致 `entryUUID` 变化时，只需要重新对应 `ExternalID`。存量账号的 UUID 不变，包括 `admin` 的固定值和现有的 `ldap:<用户名>`。UUID 只写进 JWT claims 和接口响应，代码里没有按 UUID 查用户的地方，也不解析它的前缀，所以不需要迁移，已经签发的 token 也继续有效。
- 迁移（存量账号绑定）：现有 LDAP 用户还没有 `ExternalID`。按用户名找到的目录条目，不一定是当初建这个账号的人：如果 uid 在补写前已经被复用，自动补写会把新人的标识绑到旧账号上，新人随即继承旧账号的角色和项目，之后的同步也只会把这个错误固定下来。所以存量账号**只能由管理员确认后绑定**，登录和同步都不自动补写：
  - 未绑定的存量 LDAP 账号登录时，拒绝登录，提示"账号待管理员确认，请联系管理员"，并记审计。仍然先校验 LDAP 密码，密码错误照常提示密码错误。
  - 同步预览新增"待绑定"一类：按用户名在同步结果中找到条目、读到有效标识、通过重复检测、且标识没有被其他账号占用的存量账号。每条列出 Optimus 账号（用户名、显示名、邮箱、创建时间、角色）和目录条目（显示名、邮箱、标识、`createTimestamp`），供管理员核对。
  - 辅助判断：目录条目的 `createTimestamp` 晚于 Optimus 账号的创建时间，说明这个 uid 是账号建好以后才分出去的，很可能是复用。这类条目标红，不能批量勾选，只能逐个确认。读不到 `createTimestamp` 时同样标红。时间顺序正常的条目可以全选确认。这只是提示，不拦截确认：目录做过迁移或从备份恢复时，所有条目的创建时间都会是导入时间，此时只能逐个确认。`createTimestamp` 是操作属性，查询时要显式列出。
  - 管理员确认"是同一个人"：补写 `ExternalID`，账号原有的角色和项目都保留。确认"不是同一个人"：按冲突处理（见上），旧账号停用并改名保留，新人另建账号，默认角色按人员类型决定。没有勾选的保持未绑定，下次同步继续列出。
  - 标识已被另一个账号占用时，列为冲突，不进入"待绑定"。
  - 绑定确认和"不是同一个人"的处理都记审计，写明当时两边的资料和时间比较结果。
  - 目前还没正式上线，存量账号只在测试环境。上线前执行一次同步并完成确认即可；以后若在已有用户的环境升级，要在升级后立即执行同步确认，在此之前 LDAP 用户都无法登录（`admin` 是本地账号，不受影响）。
- `ExternalID` 设唯一索引，本地用户的这个字段为空。

**写入顺序（防止旧读取覆盖新读取）**

登录同步和全量同步都会把 LDAP 读到的结果写回同一个用户。全量同步分页读取、耗时较长，两种交错都可能发生：

- 全量同步读到某人是员工后暂停；目录把他改成第三方，他登录，登录同步写入"第三方"；全量同步恢复，把旧的"员工"写回去。
- 全量同步开始后，登录同步先写入"员工"；目录随后把他改成第三方，全量同步在后面的分页才读到"第三方"。这时全量同步的数据反而更新，不能因为"全量同步开始得早"就丢掉它。

比较读取时间解决不了第二种，两次读取在时间上重叠时也分不清谁更新。所以改为**加锁，并在锁内读取**。

用一把全局的**LDAP 写回锁**，不按用户分锁。曾考虑过以目录标识为键、每个用户一把锁，但登录时一开始还不知道标识、存量账号还没有标识、预览后才出现的新条目不在快照里、同一个 Optimus 账号可能先后对应两个标识，每种情况都要单独定义锁键和核对方式，容易出错。一把全局锁没有锁键问题。

- 所有"从 LDAP 读取并写回数据库"的操作都在这把锁内完成：登录同步，以及全量同步执行时对每个人的处理。
- 登录同步：
  1. 锁外认证，并把认证结果和目录标识对应起来。现在的流程是先搜索条目、再用搜到的 DN 和密码绑定，两步之间这个 DN 可能被删除、重建成另一个人，搜索看到的标识不能证明密码属于谁。LDAP 没有"绑定并读取"的原子操作，所以在绑定前后各读一次：
     - 用服务账号按用户名搜索，得到 DN、标识 A 和条目版本 V（OpenLDAP 读 `entryCSN`，微秒精度；其他服务器读标准的 `modifyTimestamp`，秒精度；两个都是操作属性，要显式列出）；
     - 用该 DN 和密码绑定；
     - 绑定成功后切回服务账号，按同一个 DN 再读一次标识和条目版本，必须仍是 A 和 V，否则拒绝登录，提示"目录正在变更，请稍后重试"，并记审计。
     
     这项检查防的是正常运维中的竞态：用户名或 DN 在登录过程中被删除重建、分给了别人。白名单里的标识由服务器生成，不会重复使用，所以只要中间这个 DN 被删除重建过，绑定后就读不到 A。条目改名、移动都会更新条目版本，所以"先把 A 移出原 DN、把 B 移入，用 B 的密码绑定，再把 B 移走、A 移回"这种构造，前后读到的标识虽然都是 A，条目版本却变了，同样会被拒绝。通过上述核对的 A，就是"通过密码验证的那个条目的标识"。

     **信任边界与部署前提**：LDAP 绑定只认 DN，协议本身没有把认证结果与 `entryUUID` 绑定的机制，上面的核对只能缩小而不能消除风险。剩下的情况都需要目录写权限，因此作为部署前提写进上线检查清单：
     - 能改名、移动用户条目（`modrdn`、对条目的 `write`）的账号，必须同时能重置这些用户的密码。这样两种能力等价：能构造上述攻击的人，本来就能直接重置密码冒充任何人，被视为可信。
     - 上线前人工核对目录 ACL（OpenLDAP 在 `cn=config` 的 `olcAccess` 中），并在测试 LDAP 上核对一次。Optimus 无法通用地读取目录 ACL，不做自动校验。
     - 已知剩余限制：在只有秒精度 `modifyTimestamp` 的服务器上，如果在同一秒内完成"移走、移回"，并且 A 恰好在这一秒内本来也被修改过，版本可能看起来没变；从备份恢复目录导致旧标识和旧版本回来。两者都需要目录写权限，在信任边界之内处理。
  2. 拿锁，在锁内按用户名重读条目。重读得到的标识必须仍是 A，才继续：按 A 匹配账号（或首次登录建账号，建之前核对 A 和用户名都没被占用）、写数据库、提交、失效缓存、放锁，然后签发会话。
  3. 不一致（例如验证密码之后，用户名被改分给了标识 B），**直接拒绝登录**，提示"目录正在变更，请稍后重试"，并记审计。不换成 B 继续，因为通过密码验证的是 A，不能用 A 的认证结果给 B 签发会话。这种情况极少，用户重新登录即可，重新登录时会对 B 重新验证密码。
- 全量同步：分页结果只用来算出预览和"哪些人要写"。执行时逐个处理要新增、更新、停用或绑定的人，每个人：拿锁 → 重读并核对 → 写数据库、提交 → 失效他的缓存 → 放锁。人与人之间释放锁，登录可以插进来。没有变化的人不写，也不拿锁。各类对象的重读和核对方式：
  - 自动停用、范围外停用：按快照里**账号这一侧**的 `ExternalID` 做"确认缺席"查询（已删除的人没有目录条目，只能用账号已绑定的标识查），账号这一侧的标识和分类都要与快照一致。
  - 冲突：按快照里账号这一侧和目录这一侧的标识分别核对，都要与快照一致。
  - 更新：不要求出现在快照里，按执行开始时重新计算出的目录标识，在锁内按这个标识重读，核对它仍然绑定在同一个账号上，并且仍属于"更新"（不是冲突，也没有落到范围外），再写入。预览之后资料才变化的账号，照常更新。
  - 新增：同样不要求出现在快照里。执行开始时重新查询得到的新条目（包括预览之后才出现的），按其标识重读，核对这个标识和用户名都还没被任何账号占用，再建账号。
  - 待绑定：按快照里的标识重读，核对标识和用户名与快照一致、账号仍未绑定、这个标识没被其他账号占用。数据库写入带条件 `WHERE id = ? AND external_id IS NULL`，影响行数为 0 就说明已被绑定，跳过并注明原因。锁保证两次确认先后执行，条件更新保证即使锁的实现以后改变，也不会覆盖已有的绑定。
  - 未绑定账号的人工停用（无法确认）：没有目录标识可重读，核对的是 Optimus 这一侧：账号仍未绑定、状态仍是启用、仍在快照的这一类里，再停用。
  - 任何一项核对不通过：跳过这个人，执行结果注明原因。
- **执行是逐人生效的，不是整体事务**。要整体回滚，就得在一个事务里一直持锁、等完所有 LDAP 查询，同步期间所有人都无法登录，所以不这样做。保证分两段：
  - 执行开始时的全量查询（连接、分页、结果为空）出错：整次中止，不写任何数据。
  - 逐人处理时某个人的重读出错（超时、连接断开等）：**立即停止**，后面的人不再处理。已经提交的人保留，他们的修改本身是对的，并且已经生效；出错的人和未处理的人数据不变。重读出错多半说明 LDAP 出了问题，继续处理只会让每个人都再等一次超时。
  - 执行结果标为"部分完成"，列出已处理、出错、未处理的人，审计汇总记下这个状态。LDAP 恢复后重新预览、执行即可处理剩下的人，已处理的人已和目录一致，不会再出现。
  - 缓存：每个人提交后在锁内立即失效他的缓存；整次执行结束时，无论成功、部分完成还是出错退出，都在 `defer` 里再统一失效一次，错误路径不会跳过失效。
- 这样所有 LDAP 写回一个接一个发生，每次写入用的都是持锁之后读到的数据，后写入的一定是更新的数据，不依赖时钟。
- 锁内重读的资料或人员类型和分页时不同，而标识、分类都一致：按重读结果写入。
- 代价：登录同步和同步执行的逐人处理要排队，锁内包含一次 LDAP 查询，排队时间取决于 LDAP 响应时间和当时排队的人数。本设计不对等待时间做上限承诺；如果实测排队明显影响登录，再考虑加锁等待超时或分锁。全量同步还要对每个要写的人多查一次 LDAP，要写的人通常很少。
- 管理员在 Optimus 中修改的字段（状态、角色、有效期、对接人）不来自 LDAP，不需要这把锁。
- 锁在进程内，单实例部署够用；以后多实例部署时，与权限缓存失效一起改为数据库锁或分布式锁。

**资料字段**

- 对 LDAP 用户，这些字段一律以 LDAP 为准：每次同步和每次登录都会覆盖，Optimus 里只读。`UpdateUser` 要拒绝修改 LDAP 用户的这些字段。
- LDAP 里属性为空，就把对应字段清空。属性有多个值时取第一个。
- 部门保存 LDAP 里的原值，不映射成中文名。
- 本地用户（`admin`）的字段照旧可以在 Optimus 里修改。

**默认角色（D5）**

- 通过同步新建的员工账号，和首次登录新建的一样，绑定 `user` 角色。第三方账号是例外，新建时不绑定任何角色，见 3.6。
- 只在新建时绑定一次。已有用户重新同步或登录时不会补绑，管理员主动摘掉的 `user` 角色不会被加回来。
- `user` 角色保持最小权限。默认角色暂不做成可配置。

**预览与执行（D6）**

1. **预览**（只读）：分页查完 LDAP，与 Optimus 里 `source=ldap` 的用户比对，列出：
   - 新增：目录里有、Optimus 里没有。
   - 更新：显示名、邮箱、部门有变化，逐字段列出旧值和新值。
   - 停用（自动）：满足下文"自动停用的条件"的账号。
   - 无法确认：不在同步结果中，但不满足自动停用条件的账号，包括没有绑定 `ExternalID` 的存量账号、无法在整个目录中查询，以及配置变更后的第一次同步。默认不停用，管理员在预览里逐个勾选后才停用。
   - 范围外：不在同步结果中，但"确认缺席"时在整个目录的某处查到了。可能是缺少用户名、被移出了过滤条件里的组、被移到了 base DN 之外，或者 base DN 被缩小了。默认不停用，管理员在预览里逐个勾选后才停用。
   - 无法识别：缺少用户名或目录标识的条目，以及用户名或目录标识重复的条目。只要有一条这样的条目，本次同步就不停用任何人，新增和更新照常执行。预览页醒目提示"有 N 个条目无法识别身份，本次不执行停用"，并列出这些条目。
   - 待绑定：还没绑定 `ExternalID`、按用户名在目录中找到条目的存量账号，需要管理员确认，见上文"迁移"。
   - 冲突：用户名相同但 `ExternalID` 不同，需要管理员确认，见上文"身份匹配"。
   - 仅提示：目录里有，但 Optimus 里已经停用。
2. **预览快照**：前端提交的名单只说明"管理员勾了谁"，不能证明这些账号出现在预览里，也不能证明管理员看到的分类和现在一致。所以预览时，服务端保存一份快照，并返回预览 ID：
   - 快照内容：每个账号的 Optimus 账号 ID、分类、**账号这一侧**已绑定的 `ExternalID`（未绑定时为空）、**目录这一侧**对应条目的标识（没有对应条目时为空，例如已删除的人），以及预览时的 LDAP 配置摘要。确认缺席、自动停用、范围外停用都按账号这一侧的标识查询。
   - 存在进程内存里，30 分钟后过期，只能执行一次，只有发起预览的管理员能执行。服务重启后快照丢失，重新预览即可。
3. **执行**：前端提交预览 ID，以及管理员勾选的账号（范围外、无法确认、待绑定、冲突）。后端：
   - 预览 ID 不存在、已过期、已执行过、不是本人发起，或者 LDAP 配置在预览后改过：整次拒绝，提示重新预览。
   - 重新查询、重新计算，并重新做"确认缺席"。
   - 每个勾选的账号逐个核对：在快照里、快照中的分类允许勾选、重新计算后分类没变、重新读到的目录标识和快照一致。标识核对防止这种情况：管理员核对的是标识 A，执行前 uid 被分给了标识 B，账号仍属于"待绑定"，分类核对能通过，但绑定的已不是管理员看过的人。自动停用的账号同样核对：在快照里列为自动停用，并且现在仍满足自动停用条件。任何一点不符，只跳过这个账号，其他照常执行，执行结果列出被跳过的账号和原因。
   - 新增、更新不会造成破坏，按执行开始时重新计算的结果执行，不要求出现在快照里，但在锁内按重新计算出的标识重读核对，见上文"写入顺序"。停用、绑定、冲突处理会造成破坏，必须出现在快照里，标识和分类都与快照一致。
   - 管理员没在预览里看到的人，不会被停用或绑定。

**确认缺席**：不在同步结果中，不等于已经不在目录里。用 `(uid=*)` 这类条件查询时，缺少 `uid` 的条目，或者属性被读权限（ACL）挡住的条目，根本不会出现在结果里。用户也可能被移到了 base DN 之外，或者 base DN 被缩小了。所以对每个可能停用的账号，都要单独查一次：**不带登录过滤条件，并且在整个目录里查**。查询起点是目录根，从 RootDSE 的 `namingContexts` 读取，例如 `dc=optimus,dc=test`，不另设配置项。

- 有 `ExternalID` 的账号：在目录根下查 `(<id_attr>=<值>)`。查不到算确实缺席，查得到列为"范围外"。
- 还没补写 `ExternalID` 的存量账号：用户名可能已被删除或修改，查不到也不能说明人已离开，所以一律列为"无法确认"。
- 读不到 `namingContexts`，或者在目录根下查询报错（例如绑定账号没有权限查根），就列为"无法确认"。
- 可能停用的账号通常很少，逐个查询的开销可以接受。

**自动停用的条件**：以下三条全部满足，才自动停用；只要有一条不满足，就列为"无法确认"，交给管理员处理。

1. 账号已经绑定了 `ExternalID`。
2. 在整个目录里确认缺席：目录根下的查询成功，并且返回 0 条。
3. 从上次同步成功到现在，LDAP 配置（base DN、过滤条件、`id_attr`）没有改过。配置改动后的第一次同步，所有停用候选都交给管理员确认；这次同步成功之后，才恢复自动停用。为此要记下上次同步成功时的配置摘要。

残留风险：如果目录的读权限设置让绑定账号完全看不到某个条目，在整个目录里查也会返回 0 条，Optimus 无法把这种情况和"已删除"区分开。只能靠"结果为空就中止""测试连接时抽样检查"兜底，并要求绑定账号对整个目录的用户条目都有读权限。

保护规则：

- 全量查询阶段（预览，以及执行开始时的重新查询）LDAP 连接失败、查询出错、分页中途出错，或者一个人都没查到，整次同步中止，不改任何数据。执行阶段逐人重读出错时立即停止，已提交的保留，结果标为"部分完成"，见上文"写入顺序"。
- 存在无法识别身份的条目时，不执行任何停用。否则某人的 `entryUUID` 因为读权限或配置问题读不到时，会被误判为"已不在目录中"。
- 只有满足"自动停用的条件"的账号才会被自动停用。范围外和无法确认的账号，必须由管理员逐个勾选。
- 本地用户不参与同步。
- 同步只处理 LDAP 用户，不会动内置 `admin` 账号，因此不会让系统失去管理员，见 3.4"内置管理员账号"。
- 已停用的用户重新出现在目录里时，不会自动启用，由管理员决定。

审计：

- 每次同步记一条汇总，包括新增、更新、自动停用、管理员勾选停用、范围外、无法确认、无法识别、冲突的人数，以及停用是否因为存在无法识别的条目、或配置刚改过而被整体跳过或转为人工确认；执行是否为部分完成，以及出错和未处理的人。
- 每个被停用的用户另记一条状态变更，格式与手动停用的 `user.status.update` 相同。
- 每个绑定确认、"不是同一个人"的处理另记一条，见上文"迁移"。
- 执行时因快照核对不符而跳过的账号，记在汇总里。

边界情况：

- LDAP 里修改用户名（`uid`）时，`ExternalID` 不变，因此按改名处理，不会产生新旧两个账号。
- 现有的 `ldaptest` 已不在目录中，而且没有 `ExternalID`，所以第一次同步时会出现在"无法确认"里，由管理员勾选停用。可以用来验收。

### 3.4 停用规则（Q4）

- **内置管理员账号**：内置的本地 `admin` 账号（`source=local`，UUID 固定为 `00000000-0000-0000-0000-000000000001`）是永久的兜底管理员：
  - 不能停用，不能摘掉 `admin` 角色，后端直接拒绝并记审计。内置账号按固定 UUID 识别，不按用户名。
  - **`admin` 角色固定拥有全部 `system.*` 权限**（菜单和接口），在角色页不可编辑，后端拒绝修改它的 `system.*` 权限；其他模块的权限仍可编辑。这取代现在只保护 5 项核心权限的 `containsAllCoreAdminPermissions`：那份清单不含修改用户角色、修改用户状态和用户管理菜单，兜底账号可能无法完成恢复。和 GVA 的超级管理员一样，不另外维护"恢复所需权限"清单，以后新增的系统权限（如 LDAP 同步）也自动带上。`admin` 角色本身不能删除，这条现在已有。
  - **启动迁移时检查并修复**（在开始接收请求之前执行）：现有种子逻辑发现 `admin` 账号已存在就直接返回，不会恢复状态；而升级前的规则允许在有其他管理员时停用它。所以每次启动都按固定 UUID 检查：
    - 账号不存在：按现有种子逻辑创建。
    - 固定 UUID 找不到、但有用户名为 `admin` 的本地账号（只可能来自手工改库）：把它的 UUID 改成固定值，作为内置 admin 接管并记审计；UUID 不用于查找用户，已有会话不受影响。用户名为 `admin` 的非本地账号会挡住内置 admin，拒绝启动，日志给出改名的 SQL。
    - 已停用：重新启用。
    - 没有 `admin` 角色：补回。
    - `admin` 角色缺少任何 `system.*` 权限：补齐，并重新加载 Casbin。其他权限（包括云、项目模块）只在该权限首次出现在目录中时授予 `admin` 一次，管理员撤销后重启不会恢复。
    - 做了任何修复，都记审计，并在启动日志中醒目提示"内置 admin 已恢复，请确认其密码"。如果当初停用它是因为密码太弱，恢复后这个密码会重新可用，所以上线检查清单要求确认内置 admin 的密码。
  - 它是本地账号，不受 LDAP 影响。LDAP 用户怎么变化（停用、删除、转为第三方），系统都至少还有这一位可用管理员；LDAP 管理员全部失效时，用它登录，重新分配管理员。
  - 因此不再需要"最后管理员"检查：现有的 `wouldHaveAdminCapableUserAfterStatus`、`wouldHaveAdminCapableUserAfterRoles` 换成"目标是不是内置 `admin` 账号"的判断，也不需要为这个约束加锁。先检查、再提交的并发窗口随之消失。
  - 代价：它的密码是最后一道门，部署时必须设置强密码，升级后要确认。目前没有找回方式，本地账号密码管理在第 4 节，届时再加命令行重置工具。
- 用户只停用，不删除，不提供删除用户的接口。原因是审计日志、项目负责人、工单都引用了用户，删除后这些记录会对不上。这一点与 GVA 不同，GVA 支持硬删除。
- 以后增加"本人修改资料"时，只允许修改白名单内的字段。GVA 的 `SetSelfInfo` 用 `Updates(req)`，请求里带上 `enable` 也会被写入，存在被冻结但仍在线的用户自行解冻的可能。这是读代码得出的结论，没有实际运行验证。

### 3.5 审批角色（D7）

- 角色新增"可用于审批"标记（`SystemRole.Approvable`），在角色页设置。审批链配置时只能选带这个标记的角色。
- `admin` 角色不打这个标记。管理员要审批，就给自己再分配对应的审批角色。
- 审批角色本身不带菜单和接口权限，只表示"有资格审批这一级"。"我的待办"和审批操作的页面、接口放进 `user` 角色。某张工单能不能由某人审批，由后端按审批链判断，不经过 Casbin。
- 持有该角色的任意一人审批，这一级就通过（或签）。
- 种子数据预置两个审批角色，都带审批标记，都不带权限：`security-approver`（安全审批）、`dept-head-approver`（部门负责人审批）。
- 现有三级审批的对应关系：

| 审批级别 | 审批人 |
| --- | --- |
| 主管（lineManager） | 工单所属项目的负责人 |
| 安全（security） | 持有 `security-approver` 的用户 |
| 部门负责人（deptHead） | 持有 `dept-head-approver` 的用户（目录里没有部门负责人数据，暂时用角色代替） |

以下问题留到审批流设计中决定：

- 审批链按什么维度配置。
- 提单人本身就是审批人时怎么处理。
- 停用的用户不能成为审批人或项目负责人的具体做法。
- 摘除审批角色、删除审批角色时，已经流转到该级的待办怎么处理。

### 3.6 第三方人员

外包、供应商、驻场顾问等第三方人员。和员工相比，他们的账号会到期，权限要更窄，而且出了问题要能找到内部负责人。

**账号与识别**

- 第三方账号同样建在 LDAP 里（例如 `ou=people` 下的 `ou=external`），由 Optimus 同步并认证，不另建本地账号。第三方条目必须位于 base DN 以内才能登录；如果目录把外部人员放在 base DN 之外，就要调大 base DN。
- 人员类型取自 LDAP 的 `employeeType`（`inetOrgPerson` 的标准属性），属性名可配置。值在 `external_type_values` 列表里的，人员类型记为 `external`，否则记为 `employee`。和部门一样，以 LDAP 为准，在 Optimus 中只读。
- 不按 OU 判断第三方，因为目录结构一调整就会判断错。也不在 Optimus 中手工标记，因为那样和"资料以 LDAP 为准"冲突，新同步进来的第三方也会默认被当成员工。
- 已知限制：目录里没填 `employeeType` 的第三方，会被当成员工。这依赖目录管理员建账号时填对。

**Optimus 维护的管控字段**

以下两个字段由管理员在 Optimus 中设置，不来自 LDAP：

- `SystemUser.ExpiresAt`：有效期，到期后账号失效。
- `SystemUser.SponsorID`：对接人，必须是一名处于启用状态的员工，用于审计追溯，以后也用于到期前提醒。

**规则**

- 第三方账号必须同时设置有效期和对接人。缺任意一个时，加载权限时按"没有任何角色"处理：账号可以登录，但看不到任何菜单、调不了任何接口。这条规则在读取权限时统一判断，所以不管第三方是新同步进来的，还是从员工改成了第三方，都同样适用。给第三方分配角色时，如果还没设这两个字段，前端会提示先补齐。
- 到期判断复用 D1 的权限加载：每个请求都拿缓存里的 `ExpiresAt` 和当前时间比较，因此不需要定时任务，到期后下一个请求就失效。到期后的请求返回 HTTP 401，`msg` 为"账号已过期"；登录时返回 code 7 和"账号已过期"。处理方式和停用一样，但两者是独立的状态，到期不会改 `Status`。管理员延长有效期后，账号立即恢复。
- 第三方不能持有内置 `admin` 角色和审批角色（带 `approvable` 标记的角色），也不能担任项目负责人：
  - 分配角色、设置项目负责人时，后端直接拒绝。
  - 员工在 LDAP 里被改成第三方时，加载权限会忽略他的 `admin` 角色和审批角色，审批人计算也会跳过他。同步预览把这种"类型变更"列出来，并提示管理员移除这些角色、重新指定他负责的项目。类型变更总是照常写入，第三方限制立即生效；即使他原来是唯一的 LDAP 管理员，系统仍有内置 `admin` 账号兜底，见 3.4。
  - 自定义角色不受这条限制：管理员自己新建的角色即使带了用户管理、角色管理等权限，也可以分配给第三方，由管理员分配时自行把关；这类角色也不计入"可用管理员"。
- 第三方通过同步或首次登录新建账号时，不绑定 `user` 角色，由管理员按需授权。这样在目录里多建一个外部账号，不会自动拿到 Optimus 的访问权限。
- 对接人被停用或到期时，不自动处理第三方账号，只在用户列表里标出"对接人失效"，由管理员更换对接人。
- 设置或修改有效期、对接人都记审计。

## 5. 验收

- 停用用户后，该用户已登录会话的下一个请求返回 401，前端在登录页显示"账号已停用"。
- 摘除用户角色、删除角色后，下一个请求就按新的权限判断。
- 并发场景，由测试覆盖：
  - 修改接口返回之后，后续请求一律使用新权限；
  - 请求读到旧权限后，管理员撤权并清了缓存，这个请求再尝试回写缓存时被丢弃；
  - 请求在锁内比较完版本号后暂停，撤权请求要等它写完才能清缓存；撤权接口返回后，下一个请求使用新权限；
  - 修改角色接口权限后，下一个请求按新策略放行或拒绝；重载失败时的处理见下文"Casbin 重载"。
- 失效路径，每条都验证"修改成功后的下一个请求使用新权限"：
  - 员工转第三方：在 LDAP 里把已登录员工的 `employeeType` 改成 `contractor`，他重新登录（登录同步），或者管理员执行全量同步。之后该用户已有会话的下一个请求，按"第三方、缺管控字段"处理，没有任何权限，原有的审批角色也不再生效。
  - 补齐管控字段：管理员给第三方补齐有效期和对接人后，下一个请求恢复他已分配角色的权限。只补其中一项时，仍然没有权限。
  - 修改管控字段：把有效期改成已过去的时间，下一个请求返回 401"账号已过期"；再延长，下一个请求恢复。清空对接人后，下一个请求没有权限。
  - 修改角色审批标记：给第三方持有的某个角色打上审批标记后，下一个请求不再带有这个角色的权限。
- 身份无法识别：让同步范围内的某个条目读不到 `entryUUID`，或者构造两个同名条目、两个标识相同的条目。同步时新增和更新照常执行，不停用任何人，预览页给出提示。读不到标识的用户登录被拒并有审计，存量账号也一样。标识重复时登录被拒。
- 确认缺席：删掉某个已同步用户的 `uid`、把他移出过滤条件、把他移到 base DN 之外，或者缩小 base DN，他都会出现在"范围外"，不勾选就不会被停用。已经绑定标识的用户从目录里删掉后，会被自动停用。
- 修改 LDAP 配置后的第一次同步不会自动停用任何人，候选都列为"无法确认"；下一次同步才恢复自动停用。
- `id_attr` 只能从白名单里选；已有账号绑定标识时，修改 `id_attr` 会被拒绝。
- 删除角色：`admin`、`user` 不能删，还有用户使用的角色不能删，删除后 Casbin 规则被清除。
- 迁移：迁移前已停用的角色，其用户绑定被解除并留有审计；迁移后用户的实际权限不变。
- 存量账号绑定：
  - 未绑定的存量 LDAP 账号登录被拒，提示"账号待管理员确认"，并有审计；登录和同步都不会自动补写 `ExternalID`。
  - 同步预览把它们列为"待绑定"。把某个测试条目的 uid 换给一个比 Optimus 账号更晚创建的新条目，这一条标红、不能批量勾选。
  - 管理员确认"是同一个人"后补写标识，角色和项目保留，用户可以登录；确认"不是同一个人"后按冲突处理，新人只有 `user` 角色。
- 身份匹配：在目录里给某个 uid 改名后，同一账号的用户名被更新。模拟 uid 被另一个人复用时，登录被拒绝，同步预览列为冲突，管理员确认后，旧账号被停用、改名，UUID 保持不变；新账号能建出来，UUID 是随机生成的，和旧账号不同，并且只带 `user` 角色。用户名被第三方（`employeeType=contractor`）复用时，确认后新建的账号不带任何角色。
- 在测试 LDAP 上做同步：预览列出 10 个用户；执行后都出现在用户列表里，部门正确；`ldaptest` 出现在"无法确认"里，管理员勾选后被停用，并有审计记录。
- 全量查询失败或结果为空时，同步中止，数据不变。逐人处理阶段出错时按部分完成处理，见下一条。
- 部分完成，由测试覆盖：执行时第 1 个人提交后，让第 2 个人的重读超时。第 1 个人的数据已更新，他的下一个请求按新权限处理；第 2 个人和之后的人数据不变；结果标为部分完成，审计有记录；LDAP 恢复后重新预览、执行，处理完剩下的人。
- 写入顺序，由测试覆盖：
  - 全量同步分页读到"员工"后暂停，目录改为第三方，登录同步写入"第三方"；全量同步恢复后在锁内重读，写入的仍是"第三方"，下一个请求按第三方处理。
  - 全量同步开始后，登录同步先写入"员工"，目录随后改为第三方，全量同步在后面的分页读到"第三方"；执行后数据库是第三方，没有被丢弃。
  - 登录同步和全量同步执行的写入不会交叉：一方持锁时，另一方等待。
  - 用户名对应标识 A 的条目通过密码验证后、锁内重读前，把这个用户名改分给标识 B：登录被拒并有审计，没有签发会话，A、B 对应的账号都没有被写入；之后以 B 的密码重新登录，按 B 正常处理。
  - 两个管理员各自预览，一个确认某存量账号对应 A；随后用户名改分给 B，另一个确认同一账号对应 B。两次执行交错：先执行的生效，后执行的因"账号已绑定"或"标识与快照不一致"被跳过，账号的绑定没有被覆盖。
  - 预览之后才出现的新条目在执行时被新增；执行前它的用户名已被占用时跳过。
  - 无法确认类里的未绑定账号被勾选停用：执行前账号已被管理员手动停用或已被绑定时跳过，否则停用。
  - 要停用的人在执行前重新出现在目录里，执行时跳过他。
- 登录认证与标识，由测试覆盖：在"搜索之后、绑定之前"和"绑定之后、再读标识之前"分别把这个 DN 重建为另一个条目，两种情况都拒绝登录并有审计，不签发会话。
- 内置管理员：
  - 存量修复：在数据库中把内置 `admin` 停用、摘掉 `admin` 角色、删掉 `admin` 角色的部分 `system.*` 权限，启动后三项都被修复，有审计和启动日志提示。
  - 修改 `admin` 角色的 `system.*` 权限被拒绝；其他模块权限可以修改。
  - 只用内置 `admin` 登录，能完成"把某个 LDAP 用户设为管理员"的完整操作（打开用户管理页、修改他的角色）。
- 登录认证与条目版本：在测试 LDAP 上模拟"把 A 移走、B 移入、绑定、再移回 A"，登录被拒并有审计。
- 内置管理员保护：停用内置 `admin` 账号、摘掉它的 `admin` 角色都被拒绝并有审计；其他持有 `admin` 角色的 LDAP 用户可以全部停用或摘角色，之后内置 `admin` 仍能登录并重新分配管理员。唯一的 LDAP 管理员在目录中被改为第三方后，类型照常写入，下一个请求他不再有 `admin` 和审批权限。
- 快照与执行核对，由测试覆盖：已删除用户按账号侧 `ExternalID` 确认缺席并自动停用；预览之后资料才变化的账号在执行时照常更新；更新目标在执行前变成冲突或范围外时跳过。
- 预览快照，由测试覆盖：
  - 提交一个快照里没有的账号、伪造或篡改名单，这些账号不会被停用或绑定；
  - 预览后某个账号的分类变了（例如重新出现在目录里），执行时只跳过他，其他照常执行；
  - 管理员核对待绑定账号对应标识 A，执行前把这个 uid 换给标识 B 的新条目，执行时这个账号被跳过，没有绑定到 B；
  - 预览 ID 过期、重复执行、由其他管理员执行，或者预览后改了 LDAP 配置，整次被拒。
- LDAP 用户的显示名、邮箱、部门在用户管理页不可编辑，后端也拒绝修改。
- 过滤条件：`(uid={username})`、`(&(uid={username})(memberOf=...)(!(employeeType=disabled)))` 可以保存，推导出的同步过滤条件分别是 `(uid=*)` 和 `(&(uid=*)(memberOf=...)(!(employeeType=disabled)))`；`{username}` 出现在否定、或、子串、嵌套与里，或者出现多次、属性不是用户名属性，都拒绝保存。
- 测试连接：默认配置下查到同步范围内的用户并抽样读到 `entryUUID`；把 base DN 改成一个没有用户的子树，提示"同步范围内没有用户"，不再报告成功。
- Casbin 重载，由测试覆盖：
  - 注入一次重载失败后，需要接口权限的请求返回"权限系统同步中"，不按旧策略放行；后台重试成功后自动恢复，下一个请求按新策略判断。
  - 两次修改并发触发重载，先开始的那次故意延迟完成，最终内存策略和数据库一致。
  - 启动时首次加载失败不会 panic，恢复后正常鉴权。
- 审批标记可以在角色页设置；两个预置审批角色存在，且不带权限。
- 第三方人员：
  - 在测试 LDAP 中把某个用户的 `employeeType` 设为 `contractor`，同步后人员类型显示为第三方。新建的第三方账号没有 `user` 角色。
  - 第三方没有设置有效期或对接人时，能登录，但没有任何权限。两项都补齐并授权后，权限正常。
  - 把有效期设为已经过去的时间后，下一个请求返回 401"账号已过期"，登录时提示"账号已过期"；延长有效期后立即恢复。
  - 给第三方分配 `admin` 角色或审批角色、把第三方设为项目负责人，都会被拒绝；分配带管理权限的自定义角色不受限。员工改成第三方后，他的审批角色不再生效，同步预览会提示类型变更。
- 后端和前端测试按 [AGENT.MD](../../AGENT.MD#验证) 的基线通过。
