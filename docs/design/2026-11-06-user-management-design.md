# 用户管理设计

- 状态：已批准（用户逐条确认，2026-11-06）；实现状态：未开始。
- 关联：[#80](https://github.com/Dcuhddrg/Optimus/issues/80)（实施与验收）、[#4](https://github.com/Dcuhddrg/Optimus/issues/4)（审批流，以本设计为前置）、[ADR-005](../adr/0005-ldap-identity-optimus-authorization.md)（身份与授权分工）。
- 对照基线：gin-vue-admin 本地仓库 `67894b11`（比文档其他处引用的 `cee04b08` 新）。

## 1. 背景

审批流需要按"审批角色 + 项目负责人"确定审批人。核查现状时发现：

- LDAP 用户首次登录才在 Optimus 建账号（`service/system/auth.go` 的 `syncLDAPUser`），管理员无法在此之前分配角色。
- 用户状态只在登录时检查（`auth.go` 的 `Login`、`loginLDAP`）。JWT 中间件不查状态，token 临期续期时原样复制旧 claims（`middleware/jwt.go`）。
- 角色 ID 写在 token 里（`utils/claims.go` 的 `RoleIDs`），Casbin 直接用它判断（`middleware/casbin_rbac.go`）。停用用户、摘除角色、停用角色，对一直在线的用户都不生效。
- 角色的启用/停用状态（`SystemRole.Status`）是 Optimus 独有的，GVA 的 `SysAuthority` 没有这个字段。
- 测试环境的 OpenLDAP（容器 `optimus-test-openldap`，`dc=optimus,dc=test`）在 `ou=people` 下有 10 个用户，分 qa、dev、ops、sales、manger 5 个 `departmentNumber`，没有组，也没有 `manager` 属性。`ou=robots` 下是绑定用的机器人账号。

## 2. 原则

LDAP 只负责身份：认证，以及用户资料的同步。角色、审批资格、项目成员这些授权全部在 Optimus 里维护，不做 LDAP 组到角色的映射。理由和代价见 [ADR-005](../adr/0005-ldap-identity-optimus-authorization.md)。

本地账号只保留内置的 `admin`，用于 LDAP 不可用时的应急登录。

## 3. 当前阶段

### 3.1 权限即时生效（D1）

**规则**

- 用户停用、用户角色增减、角色删除、角色权限修改，都在下一个请求生效。
- 已停用用户的请求返回 HTTP 401，`msg` 为"账号已停用"。前端跳回登录页并显示这句话。
- 登录接口对已停用账号仍然返回 code 7 和"账号已停用"，与现在一致：登录接口本身不需要认证，"不允许登录"是这次请求的业务结果。
- 用户的角色被摘光时不会被踢下线，只是失去权限，访问页面时看到 ForbiddenPage。这是权限变化，不是身份失效。

**实现**

- JWT 中间件解析 token 后，按用户 ID 取出用户的当前状态和角色 ID，写入请求上下文。Casbin 中间件改用这份角色，不再读 token 里的 `RoleIDs`。token 里仍保留 `RoleIDs`，只给前端展示用。
- 取数结果放在进程内缓存里，键是用户 ID。以下操作后清缓存，保证下一个请求读到新数据：
  - 修改某个用户的状态或角色：清这个用户的缓存。
  - 删除角色、修改角色权限：清空全部缓存。
- 当前是单实例部署，也没有 Redis 消费者（见 [#55](https://github.com/Dcuhddrg/Optimus/issues/55)），进程内缓存就够用。以后改成多实例时，需要换成共享缓存或广播失效。
- token 不加入黑名单。用户重新启用后，未过期的 token 可以继续使用。
- 菜单权限码是前端在登录或获取当前用户信息时拿到的。接口权限即时生效，菜单要等页面刷新后才更新；在此期间点到已经无权访问的页面，会被接口拒绝。

**与 GVA 的差异**

GVA 的 `middleware/jwt.go` 里有"已登录用户被禁用就让 token 失效"的检查，但被注释掉了，注释写着性能考虑、需要时自行打开。GVA 给用户切换角色时，也只给操作者本人重新签发 token。Optimus 把检查默认打开，用缓存控制开销，因为"权限在 Optimus 管控"要求改动马上生效。

### 3.2 角色去掉状态，新增删除

照 GVA 处理：

- 去掉 `SystemRole.Status`、`UpdateRoleStatus` 接口、前端角色页上的启用/停用开关。`queryUserRoles` 不再按 `roles.status` 过滤。现有的 `admin`、`user` 都是启用状态，不需要迁移数据。
- 新增删除角色接口，参照 GVA 的 `DeleteAuthority`：
  - `admin` 不能删。
  - 还有用户使用的角色不能删，提示先移除这些用户。
  - 被审批链配置引用的审批角色不能删。这一条的检查在审批流实现时补上。
  - 删除时一起清掉 `sys_role_permissions` 里的关联和 Casbin 规则，然后清空权限缓存，并记审计日志。

### 3.3 从 LDAP 同步用户（D2 至 D6）

**触发（D2）**

- 用户管理页提供"从 LDAP 同步"按钮，由管理员手动触发全量同步。
- 登录时同步本人资料的逻辑保留。
- 定时同步以后再做，见第 4 节。

**范围（D3）**

- 用现有的 base DN 和登录过滤条件，把条件里的 `{username}` 换成 `*`。例如 `(uid={username})` 变成 `(uid=*)`。同步范围和能登录的范围因此是同一批人。
- 保存 LDAP 配置时，校验过滤条件里必须有 `{username}`。
- 用 LDAP 分页查询（paged results）取全部结果，不受服务端单次返回数量的限制。
- 条目里没有用户名属性的，跳过，并在预览中列出。

**字段（D4）**

| 字段 | LDAP 属性配置 | 说明 |
| --- | --- | --- |
| 用户名 | `username_attr`（现为 `uid`） | 匹配键，同步时不修改 |
| 显示名 | `display_name_attr`（现为 `cn`） | 已有 |
| 邮箱 | `email_attr`（现为 `mail`） | 已有 |
| 部门 | `department_attr`（新增，默认 `departmentNumber`，留空表示不同步） | 新增 `SystemUser.Department`；只用于展示和筛选，不参与授权 |

- 对 LDAP 用户，这些字段一律以 LDAP 为准：每次同步和每次登录都会覆盖，Optimus 里只读。`UpdateUser` 要拒绝修改 LDAP 用户的这些字段。
- LDAP 里属性为空，就把对应字段清空。属性有多个值时取第一个。
- 部门保存 LDAP 里的原值，不映射成中文名。
- 本地用户（`admin`）的字段照旧可以在 Optimus 里修改。

**默认角色（D5）**

- 通过同步新建的账号，和首次登录新建的一样，绑定 `user` 角色。
- 只在新建时绑定一次。已有用户重新同步或登录时不会补绑，管理员主动摘掉的 `user` 角色不会被加回来。
- `user` 角色保持最小权限。默认角色暂不做成可配置。

**预览与执行（D6）**

1. **预览**（只读）：分页查完 LDAP，与 Optimus 里 `source=ldap` 的用户比对，列出：
   - 新增：目录里有、Optimus 里没有。
   - 更新：显示名、邮箱、部门有变化，逐字段列出旧值和新值。
   - 停用：Optimus 里是启用状态，目录里已经没有。
   - 跳过：缺少用户名属性的条目。
   - 仅提示：目录里有，但 Optimus 里已经停用。
2. **执行**：后端重新查询并重新计算。前端把预览时列出的停用名单一起提交，后端只停用"在这份名单里，且现在仍然不在目录中"的用户，管理员没看到的人不会被停用。

保护规则：

- LDAP 连接失败、查询出错、分页中途出错，或者一个人都没查到，整次同步中止，不改任何数据。
- 本地用户不参与同步。
- 停用某人后如果系统里没有可用的管理员了，就跳过这个人并注明原因，复用 `wouldHaveAdminCapableUserAfterStatus`。
- 已停用的用户重新出现在目录里时，不会自动启用，由管理员决定。

审计：

- 每次同步记一条汇总，包括新增、更新、停用、跳过的人数。
- 每个被停用的用户另记一条状态变更，格式与手动停用的 `user.status.update` 相同。

边界情况：

- LDAP 里修改用户名（`uid`），会表现为旧账号被停用、新账号被新增。旧账号的角色和项目不会迁移过去。这种情况很少，本阶段接受。
- 现有的 `ldaptest` 已不在目录中，第一次同步时会出现在停用名单里，可以用来验收。

### 3.4 停用规则（Q4）

- 用户只停用，不删除，不提供删除用户的接口。原因是审计日志、项目负责人、工单都引用了用户，删除后这些记录会对不上。这一点与 GVA 不同，GVA 支持硬删除。
- 以后增加"本人修改资料"时，只允许修改白名单内的字段。GVA 的 `SetSelfInfo` 用 `Updates(req)`，请求里带上 `enable` 也会被写入，存在被冻结但仍在线的用户自行解冻的可能。这是读代码得出的结论，没有实际运行验证。

### 3.5 审批角色（D7）

- 角色新增"可用于审批"标记（`SystemRole.Approvable`），在角色页设置。审批链配置时只能选带这个标记的角色。
- `admin` 角色不打这个标记。管理员要审批，就给自己再分配对应的审批角色。
- 审批角色本身不带菜单和接口权限，只表示"有资格审批这一级"。"我的待办"和审批操作的页面、接口放进 `user` 角色。某张工单能不能由某人审批，由后端按审批链判断，不经过 Casbin。
- 持有该角色的任意一人审批，这一级就通过（或签）。
- 种子数据预置两个审批角色，都带审批标记，都不带权限：`security-approver`（安全审批）、`dept-head-approver`（部门负责人审批）。
- 现有三级审批的对应关系：

| 审批级别 | 审批人 |
| --- | --- |
| 主管（lineManager） | 工单所属项目的负责人 |
| 安全（security） | 持有 `security-approver` 的用户 |
| 部门负责人（deptHead） | 持有 `dept-head-approver` 的用户（目录里没有部门负责人数据，暂时用角色代替） |

以下问题留到审批流设计中决定：

- 审批链按什么维度配置。
- 提单人本身就是审批人时怎么处理。
- 停用的用户不能成为审批人或项目负责人的具体做法。
- 摘除审批角色、删除审批角色时，已经流转到该级的待办怎么处理。

## 4. 以后规划

下面这些只记录方向和触发条件，当前不排期。

| 事项 | 触发条件 |
| --- | --- |
| 本地账号创建、管理员重置密码、本人修改密码（照 GVA） | 需要 LDAP 不可用时的兜底账号，或需要给外包、服务账号开户 |
| 部门表、直属上级，审批增加"直属主管"方式 | 确认 LDAP `manager` 数据可靠；部门中文名在 Optimus 中维护 |
| 定时 LDAP 对账 | 用户量增长、手动同步跟不上；预览与保护规则运行稳定 |
| 用户列表分页、搜索、筛选（照 GVA，`PageInfo`） | 用户超过数百人，全量返回明显变慢 |
| 手机号、头像、本人修改资料 | 出现短信通知或个人中心的需求 |
| 角色层级、数据权限（GVA 有） | 出现按部门或范围查看数据的需求；目前项目隔离已够用 |
| 多实例部署下的权限缓存失效 | 后端部署多于一个实例 |

## 5. 验收

- 停用用户后，该用户已登录会话的下一个请求返回 401，前端在登录页显示"账号已停用"。
- 摘除用户角色、删除角色后，下一个请求就按新的权限判断。
- 删除角色：`admin` 不能删，还有用户使用的角色不能删，删除后 Casbin 规则被清除。
- 在测试 LDAP 上做同步：预览列出 10 个用户；执行后都出现在用户列表里，部门正确；`ldaptest` 被停用，并有审计记录。
- LDAP 查询失败或结果为空时，同步中止，数据不变。
- LDAP 用户的显示名、邮箱、部门在用户管理页不可编辑，后端也拒绝修改。
- 审批标记可以在角色页设置；两个预置审批角色存在，且不带权限。
- 后端和前端测试按 [AGENT.MD](../../AGENT.MD#验证) 的基线通过。
