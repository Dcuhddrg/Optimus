# 运维平台前端 Shell 与 LDAP 展示设计

## 背景

当前仓库主线仍然是 `server/` 下的 Go 后端骨架，`web/` 目录尚未形成成熟前端。此时如果直接同时展开完整运维平台首页、服务页、告警页、操作台、系统配置等多个页面，范围会过大，也会让第一版前端目标失焦。

本次目标不是实现完整运维平台，而是先把第一批前端展示边界收紧，确认平台壳、一级导航、Dashboard 空态和 `System > LDAP` 的页面归属与视觉方向，为后续正式实现提供稳定设计基础。

## 目标

- 明确第一版前端的一级导航范围
- 明确 `LDAP` 在信息架构中的放置位置
- 明确 `Dashboard` 第一版不做真实首页，而是保留建设中空态
- 明确前端目录结构参考 `gin-vue-admin` 的组织思路
- 明确前端技术栈为 `React + TypeScript`
- 明确第一版页面的整体视觉气质

## 非目标

- 不实现完整运维平台所有模块
- 不实现 `Services`、`Alerts`、`Operations` 等其他一级导航页面
- 不实现真实 LDAP 接入逻辑
- 不实现完整 Dashboard 数据可视化
- 不在本轮讨论中定义后端 LDAP 数据模型与接口

## 已确认的设计决策

### 子项目范围

第一版前端只聚焦两个一级入口：

- `Dashboard`
- `System`

其中：

- `Dashboard` 先做建设中空态页
- `System` 当前只展开 `LDAP`

### 技术与结构

- 前端技术栈：`React + TypeScript`
- 前端目录结构组织思路：参考 `gin-vue-admin` 的前端结构
- 参考的是目录与模块组织方式，不参考其视觉风格

### 视觉方向

整体气质定义为：

- 亮色
- 米白产品化
- 更温和、更精致
- 仍然是运维工作台，而不是品牌落地页或监控大屏

### 信息架构

当前一级导航只保留：

- `Dashboard`
- `System`

当前二级导航只保留：

- `System > LDAP`

## 页面设计

### 1. Dashboard

`Dashboard` 第一版不承载真实业务总览，也不承载假数据首页。

它的角色是：

- 平台首页入口
- 当前阶段的建设中空态页
- 为后续真实首页预留位置

第一版应呈现为：

- 页面标题
- 简短说明文字
- 清晰的“正在建设中 / Coming Soon”式空态表达
- 保留与平台壳一致的视觉风格

不应在这一页加入：

- 大量总览指标卡
- 假服务列表
- 假告警中心
- 大而全的占位模块

### 2. System

`System` 在第一版中不是一个复杂总控中心，而是平台配置能力的一级入口。

它的存在意义是：

- 承接平台级系统配置
- 为后续用户体系、认证源、权限等系统能力预留空间
- 在当前阶段为 `LDAP` 提供合理的信息架构归属

### 3. LDAP

`LDAP` 必须放在 `System` 的拓展栏下，而不是放在：

- `Dashboard`
- `Services`
- `Operations`
- `Alerts`

原因是：

- LDAP 本质上是平台级认证源能力
- 它属于系统配置域，而不是运维工作台首页内容
- 这种归类方式更利于未来扩展其他认证与用户管理能力

第一版 `System / LDAP` 页面只做静态配置页壳子，用于确认页面结构与归属，不代表真实功能开始实现。

建议页面包含：

- 页面标题与简短说明
- 连接配置分组
- 同步与状态分组
- 一两个操作按钮占位，例如连接测试
- 范围说明，例如“当前先聚焦登录认证与用户信息同步，不做角色映射”

## 页面层级关系

建议第一版前端层级如下：

```text
App Shell
├── Dashboard
│   └── Empty State
└── System
    └── LDAP
        └── Static Configuration Page Shell
```

## 视觉原则

### 整体风格

- 以米白、暖灰、浅蓝点缀为主
- 避免传统后台的厚重深色感
- 避免品牌落地页式的强装饰
- 保持产品化、长期可使用的控制台气质

### 布局原则

- 左侧导航保持清晰克制
- 主内容区以可读性和层级优先
- 不使用过量图表或花哨装饰来假装“完整平台”
- 空态页与配置页壳子都要保持统一视觉语言

### 交互原则

- 第一版展示以结构确认优先
- 不假设完整真实功能已存在
- 即使是静态展示，也要让用户一眼看出页面归属和下一步扩展方向

## 数据层策略

当前这部分设计以展示为主，因此：

- `Dashboard` 不接真实数据
- `LDAP` 页面不接真实接口
- 页面可以用静态文本与占位状态表达页面用途

后续如果进入实现规划，再单独决定：

- 哪些内容接当前后端
- 哪些内容继续保留 mock
- LDAP 的真实后端能力边界

## 与现有仓库的关系

这次前端设计需要遵循当前仓库事实：

- `server/` 仍是现阶段主开发面
- `web/` 仍处于前端待建设状态
- 当前不应误导为“完整平台已经存在”

因此，这份设计刻意选择：

- 少量一级导航
- 明确的空态 Dashboard
- 明确的 `System > LDAP` 归属

而不是直接铺开完整运维平台所有模块。

## 风险与控制

### 风险 1：第一版前端范围失控

如果把 `Services`、`Alerts`、`Operations` 同时拉进来，前端第一版会立刻膨胀。

控制方式：

- 第一版只保留 `Dashboard` 与 `System`
- 只展开 `System > LDAP`

### 风险 2：Dashboard 被假数据撑满

如果在首页塞入大量假数据模块，会让设计看起来像“完成了”，但实际无法指导后续落地。

控制方式：

- `Dashboard` 第一版明确为空态页

### 风险 3：LDAP 放错层级

如果把 LDAP 放到首页或运维工作区，会混淆“系统配置”和“日常运维”的边界。

控制方式：

- 固定放在 `System` 拓展栏下

## 验收标准

完成这份设计后，应满足：

- 第一版前端范围被明确限制为 `Dashboard + System`
- `Dashboard` 被明确为建设中空态页
- `LDAP` 被明确放在 `System` 拓展栏下
- 前端技术栈被明确为 `React + TypeScript`
- 前端目录结构参考 `gin-vue-admin` 的组织方式，但不继承其视觉风格
- 整体视觉方向被明确为亮色、米白产品化运维工作台
