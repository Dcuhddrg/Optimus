# 前端中英文切换设计

## 背景

Optimus 现有前端已经具备登录页、导航壳子和系统管理页面，但界面文案基本为英文硬编码，缺少统一的语言状态管理。当前仓库也没有现成的国际化依赖或语言上下文层。

本次目标是在不改后端接口和数据库模型的前提下，为现有前端补齐第一版中英文切换能力，覆盖登录前后主要界面，并保证系统管理页面中基于稳定 `code` 的展示项也能随语言切换显示。

## 目标

- 支持简体中文和英文两种界面语言
- 支持登录页右上角切换语言
- 支持登录后顶部栏右侧切换语言
- 支持首次访问按浏览器语言自动选择，无法识别时回退英文
- 支持用户手动切换后持久化到 `localStorage`
- 支持现有前端固定文案的统一翻译
- 支持基于稳定 `code` 或枚举值的系统展示项本地映射翻译
- 保持现有登录态、路由和接口协议不变

## 非目标

- 不改后端返回的错误消息内容
- 不要求后端接口直接返回双语字段
- 不修改数据库里的角色名、权限名或 LDAP 配置说明字段
- 不引入新的国际化 npm 依赖
- 不扩展到中英文以外的更多语言
- 不在第一版里重做页面视觉样式

## 范围

第一版覆盖以下前端界面和文本来源：

- 登录页
- 应用壳子顶部栏
- 左侧导航
- Dashboard 占位页
- Forbidden 页
- Users、Roles、LDAP、Audit Logs 页面中的固定文案
- 状态值、来源值、角色 `code`、权限 `code`、菜单 `code` 等可稳定识别的展示项

第一版不处理以下内容：

- 后端原样返回且缺少稳定映射键的自由文本错误消息
- 数据库存储的任意人工描述文本的双语维护

## 设计原则

- 保持实现轻量，优先复用现有 React 结构，不引入外部国际化框架
- 固定文案和“基于 code 的显示文案”分层处理，避免页面里混入大量条件分支
- 未识别到映射项时优先回退原始值，保证页面仍然可用
- 语言切换只影响展示层，不影响业务状态、接口参数和登录流程
- Provider 作用域覆盖登录前和登录后页面，避免出现两套语言状态

## 总体方案

前端新增一个轻量 `locale` 层，由三部分组成：

- `LanguageProvider`：维护当前语言、初始化逻辑、持久化逻辑和切换方法
- `useI18n()`：向页面提供 `locale`、`setLocale()` 和 `t(key)` 能力
- 词典与映射层：负责固定文案词典，以及系统域 `code` / 枚举值的本地显示名映射

Provider 挂在前端路由根部，保证登录页和应用内页面共享同一份语言状态。语言切换时通过 React 状态更新触发页面重新渲染，不要求刷新浏览器。

## 语言状态模型

支持的语言：

- `zh-CN`
- `en`

初始化优先级：

1. `localStorage` 已保存语言
2. 浏览器语言
3. 默认回退 `en`

浏览器语言识别规则：

- 命中 `zh` 前缀的浏览器语言时，使用 `zh-CN`
- 其余情况统一回退 `en`

持久化规则：

- 用户手动切换语言后，立即写入 `localStorage`
- 页面刷新后优先读取持久化值

建议本地存储键：

- `optimus.locale`

## 组件与落点

### Provider

`LanguageProvider` 放在路由根部，与现有 `AuthProvider` 同层或外层，确保：

- 登录页可读取和切换语言
- 应用壳子可读取和切换语言
- 认证前后切换不丢失当前语言

### 语言切换控件

新增复用型 `LanguageSwitcher` 组件，使用同一套语言状态和切换逻辑。

落点：

- 登录页右上角
- 顶部栏右侧，位于当前用户信息和退出按钮区域

交互要求：

- 清晰显示当前语言
- 点击后可在 `中文` 和 `English` 之间切换
- 切换后当前页即时更新

### 页面接入方式

页面层只通过两种方式取展示文案：

- 固定文案：`t('...')`
- 系统展示项：`getXxxLabel(value, locale)` 之类的 helper

页面中不直接编写 `locale === 'zh-CN' ? ... : ...` 分支，避免翻译逻辑散落。

## 词典结构

词典按领域组织，避免按页面任意散放：

- `common`
- `auth`
- `shell`
- `dashboard`
- `system.users`
- `system.roles`
- `system.ldap`
- `system.audit`
- `system.forbidden`

词典只负责固定文案，例如：

- 页面标题、副标题、说明文案
- 按钮文案
- 字段标签
- 空态提示
- 加载中状态
- 前端生成的错误提示

词典 key 采用稳定命名，不直接使用英文句子作为 key，避免后续维护困难。

## 系统数据映射策略

### 枚举值映射

以下值使用本地映射表：

- 用户状态：`enabled` / `disabled`
- 角色状态：`enabled` / `disabled`
- 用户来源：`local` / `ldap`
- 权限类型：`menu` / `api`

### Code 映射

以下展示项使用稳定 `code` 做本地映射：

- 菜单权限 code
- API 权限 code
- 角色 code

映射来源是前端本地定义的 label 表，不修改后端返回结构。页面渲染时按当前语言展示对应 label。

### 回退规则

当遇到以下情况时，页面必须可降级：

- 词典 key 不存在：回退 key 或约定的默认文案
- `code` 映射不存在：回退原始 `code`
- 枚举值映射不存在：回退原始值

回退规则的目标是保证功能完整可用，而不是强行隐藏未知内容。

## 文案处理边界

第一版前端接管三类文案：

- 前端组件里的固定文案
- 前端本地可识别的枚举值
- 前端本地可识别的稳定 `code`

第一版不接管以下文案：

- 后端直接返回的原始错误消息
- 缺少稳定标识的自由文本数据

这意味着：

- 登录失败等由前端生成的默认提示可以双语化
- 后端返回的原始消息若直接显示，则仍保持后端原样

## 页面覆盖要求

第一版至少应接入以下页面：

- 登录页
- AppShell 顶部栏
- 侧边导航
- Dashboard 占位页
- Forbidden 页
- Users 页面
- Roles 页面
- LDAP 页面
- Audit Logs 页面

如果页面里同时存在固定文案和系统展示项，两类都要完成切换。

## 对现有代码结构的影响

新增内容预计包括：

- `locale` 目录或等价模块
- 语言 Provider / hook
- 词典文件
- 系统展示项映射 helper
- 语言切换组件

调整内容预计包括：

- 路由根组件接入 Provider
- 登录页接入切换控件和词典
- AppShell 接入切换控件和词典
- 导航和系统页面接入 `t()` 与 label helper

本次不要求对 API client、AuthContext 或后端接口协议做结构性调整。

## 测试与验证

第一版至少验证以下场景：

- 首次进入时按浏览器语言选择语言，未知语言回退英文
- 用户切换语言后写入 `localStorage`
- 刷新页面后仍保留用户上次手动选择
- 登录页文案切换正常
- 顶部栏和导航文案切换正常
- 至少一个系统页面中的固定文案切换正常
- 至少一个系统页面中的 `code` 映射展示项切换正常
- 未知 `code` 或枚举值时回退原始值
- 前端构建继续通过

验证方式以现有前端构建和必要的前端单元级验证为主；如果仓库当前没有测试框架，第一版至少保证 `npm run build` 通过，并补充最小可行的逻辑测试或手工验证说明。

## 风险与约束

- 当前仓库没有现成国际化依赖，轻量自研方案适合当前范围，但后续如扩展多语种，需要重新评估抽象边界
- 系统数据映射依赖稳定 `code`；如果后端未来新增 code 而前端未同步映射，会以原始值回退显示
- 不翻译后端原始错误消息意味着中英文体验不会 100% 完整，但可以保持接口边界稳定

## 实施建议

建议按以下顺序落地：

1. 建立 Provider、词典和基础工具
2. 接入登录页和 AppShell，确认切换链路与持久化正确
3. 接入导航和基础公共页面
4. 接入系统管理页面固定文案
5. 接入系统展示项 `code` / 枚举映射
6. 进行构建和手工切换验证

这样可以先验证根能力，再逐步扩展页面覆盖，避免一次性替换全部文案导致排障困难。
