# `.codex/project_rules.md` 对齐更新设计

## 背景

仓库当前的 `.codex/project_rules.md` 仍然保留了一部分早期执行约定，但最近几轮真实工作方式已经发生变化。当前文件中至少有三类内容与现状不再一致：

- 将 `brainstorming → writing-plans → executing-plans` 写成固定默认链路，但实际执行中经常使用 `subagent-driven-development`
- 将 `cd web && npm install` 写成前端默认验证基线的一部分，导致“安装依赖”和“验证改动”边界混淆
- 将 Git 提交约定写成 `feat(web): 中文描述`，但当前仓库已经采用 Lore protocol 风格提交

同时，文件中也存在少量与上层代理规范重复、容易冲突或命令式过强的表达。用户本次目标不是重写规则体系，而是做一次保守对齐：继续保留该文件作为 Claude Code 与 Codex 共用契约，但把内容更新到和当前仓库真实工作方式一致，并顺手清理明显过时项。

## 目标

- 保持 `.codex/project_rules.md` 作为 Claude Code 与 Codex 共用的仓库级行为契约
- 保留当前章节结构，不重构成全新文档体例
- 将工作流描述同步到当前真实 superpowers 执行方式
- 将前端验证基线同步到当前更合理的默认验证边界
- 将提交规范同步到当前仓库实际使用的 Lore protocol
- 删除或弱化明显过时、重复或容易与上层规范冲突的条目

## 非目标

- 不把 `.codex/project_rules.md` 改造成单一代理专用规则
- 不重写 AGENTS、架构文档或其他仓库级治理文档
- 不新增与本次问题无关的大量边界条款
- 不把规则文件改造成极简版或完全重组结构
- 不在本次更新中修改实施代码、脚本或 CI 行为

## 设计原则

- 以“对齐现状”为第一目标，而不是追求格式重构
- 保持章节骨架稳定，降低历史阅读成本
- 仓库规则只写仓库级补充约束，不大段重复上层代理规范
- 对重复约束优先做弱化和收口，而不是堆叠更多命令式语言
- 保守修改，优先修正会误导执行的条目

## 更新范围

本次只修改 `.codex/project_rules.md`，不修改其他规则体系文件。

影响内容限定为以下四类：

1. 同步真实工作流
2. 清理过时验证规则
3. 对齐当前提交规范
4. 删除或弱化重复、冲突风险高的表述

## 保留的文档结构

本次更新后，文件仍保持以下章节骨架：

- `BOUNDARIES`
- `DEFAULT EXECUTION`
- `WORKFLOW`
- `VERIFICATION`
- `OUTPUT CONTRACT`
- `ARCHITECTURE REFERENCE`

不新增新的顶层结构，也不改成完全不同的治理模板。

## 章节级更新设计

### BOUNDARIES

该章节总体保留，仍然作为“默认禁止事项”和“必须暂停提问的情况”列表。

保留重点：

- 不修改任务未涉及文件
- 不顺手扩展需求
- 不更改现有技术选型或依赖版本
- 不跨越模块边界执行改动
- 前端新增一级导航、扩页面范围或改技术栈时必须确认

处理方式：

- 尽量不新增新边界
- 只做措辞清理，避免和上层代理规则形成双重命令

### DEFAULT EXECUTION

该章节保留，但语气从“对话动作指令”调整为“默认执行偏好”。

保留重点：

- 小步修改，边改边验证
- 优先贴合现有模式，不自行发明新层次
- 只在任务直接需要时新增依赖、测试或文档
- 不主动扩展已确认的前端页面范围

建议调整：

- 弱化“先用一句话复述任务范围”这类会被上层代理规范覆盖的对话要求
- 保留“明确文件边界”“任务无歧义时直接执行”等执行导向描述，但写得更中性

目标是让该章节继续指导仓库内执行习惯，而不是与代理级对话规范竞争解释权。

### WORKFLOW

该章节是本次主修改点。

当前问题：

- 文件将 `brainstorming → writing-plans → executing-plans` 写成默认固定链路
- 与仓库当前实际使用的 `subagent-driven-development` 形成偏差

更新目标：

- 保留 `brainstorming` 和 `writing-plans` 作为非平凡任务的前置链路
- 将实施阶段改成“根据任务形态选择 `subagent-driven-development` 或 `executing-plans`”
- 避免把某一个执行技能写成唯一默认终点

更新后的意图应表达为：

- 非平凡任务优先从 `brainstorming` 开始
- 形成 spec 后进入 `writing-plans`
- 有计划后的实施可按任务形态选择：
  - `subagent-driven-development`
  - `executing-plans`

这既对齐当前真实实践，也不会排斥未来不同执行路径。

### VERIFICATION

该章节保留验证原则和后端基线，但调整前端默认验证边界。

保留重点：

- 改了什么，就验证什么
- 未验证前不声称完成
- 环境阻塞时要明确说明
- 文档和规则类改动也需要验证边界

后端验证基线保持不变：

- `cd server && go test ./...`
- `cd server && go build ./...`

前端验证基线修改为：

- `cd web && npm run build`

从“默认验证基线”中移除：

- `cd web && npm install`

原因：

- `npm install` 属于环境准备或依赖变更处理，不应作为每次前端改动的默认验证动作
- 只有在依赖缺失、锁文件变化或本地环境不完整时，才应额外执行安装

保留追加验证：

- 需要运行效果时：`cd web && npm run dev`
- 需要确认访问性时：验证 dev server 可访问

纯文档或规则文件改动的验证方式保持保守：

- 检查目标文件存在
- 检查章节结构、引用关系和内容边界
- 检查未误改无关文件

### OUTPUT CONTRACT

该章节整体保留，继续约束中文输出、简洁可扫描、结论优先等仓库级沟通偏好。

保留重点：

- 对话使用中文
- 结果汇报保持简洁
- 结论先于过程
- 若发现额外问题，先完成当前任务再简述
- 前端展示任务优先说明页面范围、导航边界和是否为静态壳子

默认汇报格式可以继续保留，因为它对仓库协作仍然有价值。

本次主修改点是 Git 提交约定。

当前问题：

- 文件仍使用 `feat(web): 中文描述` 作为默认提交规范
- 与当前仓库实际采用的 Lore protocol 不一致

更新目标：

- 删除旧的 Conventional Commit 中文格式约定
- 改为明确要求：提交信息遵循仓库当前 Lore protocol
- 如需示例，只提供 Lore 风格示意，不再给旧格式示例

这样可避免规则文件继续误导代理使用过时提交格式。

### ARCHITECTURE REFERENCE

该章节不改。

继续保留：

- 架构事实统一维护在 `docs/architecture/current-architecture.md`
- 规则文件不重复维护架构快照

## 拟删除或弱化的内容

本次不会大删章节，但会删除或弱化以下类型内容：

- 与上层代理规范重复的强命令式对话动作
- 已与当前仓库实践冲突的固定执行链路描述
- 把环境准备动作误写成默认验证基线的条目
- 已过时的 Git 提交格式示例

目标不是把文件删短到极简，而是只去掉会误导执行的内容。

## 风险与控制

### 风险

- 若过度精简，文件会失去仓库级补充约束价值
- 若过度扩写，又会与 AGENTS 或代理系统规范形成重复
- 若工作流描述写得过死，未来再次演进后又会快速过时

### 控制方式

- 保留原有章节骨架
- 只修改已经被现实执行证明失真的条目
- 对共享边界采用中性表述，不复制上层代理长规则
- 工作流只写“推荐路径”和“可选实施方式”，不写唯一终点

## 验证设计

本次属于纯规则文件更新，验证方式应以结构和边界检查为主：

- 检查 `.codex/project_rules.md` 存在且章节结构仍完整
- 检查仅修改该文件，不误改无关仓库规则文件
- 检查工作流、验证、提交规范三类关键内容是否已与当前现状对齐
- 检查未再保留过时 `npm install` 前端默认验证基线
- 检查未再保留旧的 `feat(web): 中文描述` 提交规范

## 预期结果

更新完成后，`.codex/project_rules.md` 应具备以下状态：

- 仍然是 Claude Code 与 Codex 共用的仓库级契约
- 章节结构和阅读习惯保持稳定
- 内容不再误导代理走过时工作流
- 前端验证基线更合理
- Git 提交规范与当前 Lore protocol 对齐
- 与上层代理规范的冲突和重复减少
