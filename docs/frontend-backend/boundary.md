## 2. 前后端职责与协作

参考 gin-vue-admin 的 [边界说明](https://github.com/flipped-aurora/gin-vue-admin/blob/main/aiDoc/frontend-backend/boundary.md)、[前端约束](https://github.com/flipped-aurora/gin-vue-admin/blob/main/aiDoc/frontend-backend/frontend-rules.md)和[工具函数约束](https://github.com/flipped-aurora/gin-vue-admin/blob/main/aiDoc/frontend-backend/frontend-utils.md)，结合 Optimus 的 React + TypeScript 技术栈执行；不引入上游 Vue、Pinia 或其专用组件库。

| 责任方 | 职责 |
| --- | --- |
| 后端 | Router 注册与中间件，API 绑定和校验请求、转换响应，Service 实现业务规则与授权相关逻辑，Model 定义数据结构；服务端是权限及项目隔离的最终执行方 |
| 前端 | 路由和页面流程、表单交互、展示与本地状态；通过模块 API 和明确类型对接服务端，权限控制用于改善体验，不代替服务端校验 |
| 共同 | 以请求、响应、字段、错误及权限约束为接口契约；变更时核对实现、调用方和 Swagger，分清既有行为与目标 |

需求涉及接口时先确定路径、方法、请求参数、响应 DTO、HTTP/业务错误、认证与项目范围；破坏性变更还要列出受影响调用方、发布顺序与回退方式。Swagger 与实际行为冲突时以实测和代码为当前事实，修正不一致后再作为接口依据。

## 3. 当前实现与差异

| 场景 | 当前行为 | 迁移时需要保护的调用 |
| --- | --- | --- |
| 登录、当前用户 | 原始 DTO，未套统一 envelope | 登录结果的 token、用户及权限字段，现有会话读取 |
| 用户、角色列表 | `{items,total}` | 不因存在 total 就宣称支持分页 |
| 权限树 | `{items}` | 树形集合不自动改为分页 |
| 项目、成员列表 | 服务端 `{items}`；客户端 ListResponse 额外要求 total | 修正真实类型或明确服务端新契约，不能编造已有字段 |
| 云账号列表 | `{items,total}`，当前不是分页查询 | 保留筛选和计数含义 |
| 云资产、审计查询 | `{items,total,page,pageSize}` | 迁移 items/list 时同步参数、类型及页面；审计客户端尚无分页参数入口 |
| 删除、登出等提示 | 部分返回 `{message}` | 明确无业务数据操作的目标 data 值 |
| 错误 | HTTP 4xx/5xx 与 `{message}` | 当前客户端只读 message，以 HTTP 状态判断失败 |
| CSV、探活 | CSV 文本与现有 health/ping 小响应 | 保留内容类型、下载和探活调用 |

当前 `apiRequest` 原样返回 JSON，并在所有 401 时清理凭据；它尚不理解 envelope 的 code/msg。后续适配不能通过 `body.data ?? body` 猜测协议，业务数据可能含有同名字段，data 也可能为 null、0 或 false。

## 4. 目标响应与 HTTP 语义

以下为拟实施契约，**不是当前所有接口的返回格式**。

| 字段 | 目标约定 |
| --- | --- |
| code | 整数；成功为 0、失败为 7。扩展业务码需同步文档和客户端，不由页面猜测 |
| data | 必须存在；成功返回已声明 DTO/集合/分页数据。无业务数据及失败时建议为 null，见待确认项 D1 |
| msg | 字符串，供人阅读；失败提供摘要，前端不依赖文案判断权限或业务分支，不暴露凭据及内部 SQL 等细节 |

成功示例：

```json
{"code":0,"data":{"id":1,"name":"示例项目"},"msg":"成功"}
```

失败示例（HTTP 403，data=null 为本次提案）：

```json
{"code":7,"data":null,"msg":"无权访问该项目"}
```

- 保留已有成功 HTTP 状态和各接口业务含义；错误不改为 HTTP 200 来掩盖失败。
- 400 表示请求不合法，401 表示认证失败，403 表示无权限，404 表示资源不存在，409 表示冲突；已有 422、500、503 等语义继续按实际场景使用，不机械改码。
- 已迁移 JSON 接口的成功响应同时满足 HTTP 2xx 与 code=0；非 2xx 始终失败。意外出现 HTTP 2xx/code=7 也必须拒绝，不能误当成功。
- JSON 解析失败、字段缺失或类型不符按协议错误处理，不冒充正常业务数据。错误对象应保留 HTTP 状态和可用业务码，便于上层分类。
- msg 不是状态码，也不是默认的 i18n key；前端用自身语言资源处理通用 fallback。

## 5. 集合、分页与字段

分页数据放在 envelope 的 **data 内**，不是与 code/msg 平级：

```json
{"code":0,"data":{"page":1,"pageSize":20,"total":0,"list":[]},"msg":"成功"}
```

- 真正分页的接口返回 page、pageSize、total、list；total 为完整筛选结果数，不是当前页长度，空页返回 list=[]，保留真实 total。
- 当前资产和审计查询采用 page 从 1 开始、默认 pageSize=20、范围 1～200；非法值回退默认。目标沿用这一约定，新模块的分页能力须明确实现及验证。
- 普通集合建议返回 `data: { list: [] }`；业务需要计数时可声明真实 total，但不伪造 page/pageSize。权限树和非分页项目集合不能只为结构统一强行分页化。
- 新增 JSON 字段使用 camelCase；现有字段名和类型保持调用方一致，重命名放在明确的迁移批次，不全局批量替换。
- 集合为空返回数组，不用 null 代替；可选与 nullable 分开声明，不把字段缺失、null、空字符串混为一种状态。无实体 data 值待 D1 确认。
- 时间使用带时区的 RFC3339/ISO 字符串，前端负责展示本地化；现有 ID 类型先保持不变，超出 JavaScript 安全整数范围等问题需单独明确，不能默默截断或改类型。

## 6. 请求、认证与权限协作

- view 通过 `web/src/api/` 的模块函数发请求；目前公共封装固定 `/api/v1`，后端 RouterPrefix 的自定义能力不等于前端 base URL 已自动适配。
- JSON 请求使用 Content-Type: application/json；GET 参数通过明确的查询类型编码。不要把未定义字段、空字符串和 undefined 当成同一种查询条件。
- 认证沿用 Authorization: Bearer token。X-Project-Code 表示资源项目选择，不是授权凭证；后端仍执行 JWT、RBAC、成员资格及项目隔离检查。
- 云资源使用项目范围；系统和项目恢复入口不因无关的过期项目选择被拦截，保持 #12/#13 的修复行为。项目管理按路径项目独立鉴权。
- 目标错误分类：已登录私有请求明确 401 才触发凭据失效流程；登录表单的 401 显示认证失败，不无条件注销另一会话；403 不注销用户，失效项目选择提示重新选择。
- 网络错误、5xx 或解析异常不直接证明 token 失效；保留凭据并提供可重试错误，同时不把尚未确认的用户状态显示成认证成功。当前会话恢复逻辑仍有差异，行为整改需单独验证。
- 通用请求层不对非幂等写操作自动重试，防止创建、同步等动作因重试重复执行。

## 7. CSV、探活与无正文例外

- CSV 成功响应保留 text/csv 和 Content-Disposition，不包 JSON envelope。导出使用明确的下载适配器，先检查 HTTP 状态及 Content-Type；失败可能是 JSON，不能将错误内容当文件或对 CSV 无条件 JSON.parse。
- health/ping 保留现有响应和探活行为，不随业务 envelope 批量改造。
- 其他上传、流式或非 JSON 接口存在时，必须独立声明内容类型及错误方式，本提案不假定这些能力已实现。
- 已声明的 JSON 操作不通过省略整个响应正文代替 data；若保留 204 等无正文响应，应明确列为例外并使用相应适配器。

## 9. 客户端适配与迁移步骤

1. 先确认 D1、D2 并为迁移模块登记路由、旧/新 payload、调用方、异常与回退条件。
2. 公共层区分 HTTP 失败、业务失败和协议失败；旧请求继续按明确的旧契约处理，新请求仅通过显式选定的适配器严格解析 envelope。不要根据返回对象形状自动切换模式。
3. 迁移期可在明确的 HTTP 错误分支兼容读取 msg/message 以展示错误；这种兼容不能变成成功 payload 的隐式解包。JWT/RBAC/ProjectScope 等跨模块错误也要纳入清单。
4. 按模块同批修改后端 DTO/响应、前端 API 类型及必要页面调用、相关文档和测试。items→list 的过渡映射如有需要，应放在明确的模块边界，记录退出条件。
5. 登录、当前用户和其他公共依赖先补特征测试，按依赖顺序迁移；CSV 和探活单独验证。不通过新增一层全局响应中间件一次包裹全部路由。
6. 代码迁移继续由 #11 下独立子项实施；结构迁移保持现有 wire 行为，不能因本文件存在就自动改响应。旧调用兼容方式未确认前，不默认创建版本路由或协商 header。

1. 路由、方法、参数、字段和类型与真实实现一致；Swagger 已同步，兼容及回退方案有明确负责人和退出条件。
2. 前端调用、页面状态、错误展示和权限入口与服务端行为一致；鉴权和项目隔离由后端实际验证。
3. 目标契约及涉及的模块设计已更新；当前行为与已实施范围有证据，不以文档存在代替代码验收。
4. 运行与改动相关的测试和构建，记录未覆盖或受阻场景；有页面交互变更时按实际影响验证主要操作、失败及空状态。
