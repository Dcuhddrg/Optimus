# ADR-002：统一存量后端结构，取消旧方案长期豁免

- 日期：2026-10-27。
- 状态：规范方向已由用户明确确认；迁移实施和验收见 [Issue #11](https://github.com/Dcuhddrg/Optimus/issues/11)，本记录不宣称代码迁移已完成。
- 取代：[ADR-001](archive/ADR-001-backend-layering.md) 中将旧 usecase/infra 长期作为 Service 内部组织保留、仅统一文档而不要求迁移存量的约定。
- 规则入口：[AGENT.MD](../../../AGENT.MD)；职责与路径要求：[当前架构](../../modules/backend-layer-rules.md#后端分层契约)。

## 决定

新模块与存量模块共同遵循 `Router -> API -> Service -> Model`，统一职责、目录、包依赖和注册入口。旧 usecase/infra 必须分批迁移，不再存在长期保留的例外。

迁移按模块列明旧路径、新路径、调用方、接口和测试；业务逻辑归 Service，实体与数据结构归 Model，数据访问和外部适配按确认后的职责归位。可以保留必要的测试与解耦接口，不能用接口或目录别名延续另一套平行架构。

## 执行与完成标准

- #11 先完成模块/依赖清单和样板方案，再逐模块实施；project 可作为首个候选，具体顺序以依赖核查和 Issue 排期为准。
- 每批同步修改 API 调用、服务构造、enter.go、初始化注入、测试与相关说明，保持已有行为和授权边界。
- 临时兼容入口必须记录用途及删除条件，在相应迁移子项关闭前清除；目标模块的旧目录和旧包引用不得继续残留。
- 构建、隔离 MySQL 回归及相关竞态/路由验证通过，并取得用户验收。历史文档可出现旧名称，不能再作为代码豁免依据。

## 排期边界

用户后续明确恢复 #7 的契约文档工作，文档可先于结构迁移完成，用于定义对外行为与迁移边界。结构迁移期间保持当前接口行为，响应格式代码改造仍作为独立批次实施。

已确认的 HTTP 4xx/5xx 语义及成功码 0、失败码 7 保留；已确认的分模块切换方向及实施细则见 [接口契约](../../frontend-backend/boundary.md)，不作为本批默认代码实施方案。

#12/#13 已验收修复及其测试证据继续有效，迁移必须保留其行为。旧计划中“本批不迁移”等表述仅描述当时的交付范围，不再限制后续 #11 的结构迁移。

当前授权先整理规范与计划；本次文档变更不搬动业务代码，不包含新增功能、数据库结构修改、部署配置变更或依赖升级。
