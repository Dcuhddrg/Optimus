# 文档与 Issue 维护约定

最近更新：2026-10-29。本文规定 Issue 与各类文档记录什么、何时更新及如何标注状态；开发顺序见 [开发工作流](development-workflow.md)，协作职责、授权及验收边界见 [AGENT.MD](../../AGENT.MD)。

## 各自负责什么

- [GitHub Issues](https://github.com/Dcuhddrg/Optimus/issues)：所有 Bug、反馈、需求建议、架构风险、待决策事项的来源、优先级、责任、进度、讨论和验收记录。
- 路线图：长期目标、阶段依赖和非目标；架构/ADR：当前约束、重要取舍及理由。
- spec：场景、范围、异常行为、验收条件；plan：实施步骤。已确认的重要讨论结论写回相关设计，不要求读者遍历 Issue 评论重建设计。
- 能力状态表：实现与验证证据，链接相关 Issue，不复制 Issue 的处理状态和待办清单。
- 决策索引维护现行决定及依据；已移除的历史内容按需通过 Git 历史和 Issue 追溯。

## 更新时机

- 重要讨论形成已确认结论时，写回相关设计或 ADR，并保留依据及替代关系。
- 业务或架构发生变更时，复核关联设计并更新受影响内容。
- 取得新增实现或验证证据时，更新能力状态表中的对应条目，注明核查日期、基线及未覆盖项。
- 任务结束时，在 Issue 记录结果、提交/PR、验证命令和覆盖范围；结案依据根规则的验收要求记录，不用合并自动关闭代替验收。

## 状态与事实

- Issue 保持打开，正文的“阶段”记录待评估、已确认、处理中或待验证；结案才关闭，并注明完成或不采纳理由。优先级用 P1/P2/P3 或待评估，未分配责任如实写待分配。
- 设计状态：草稿 / 待确认 / 已批准 / 已取代；计划状态：待执行 / 执行中 / 执行完待验证 / 已验收。历史批准记录保留，不补造批准人或时间。
- 实现状态：待核实 / 未开始 / 部分实现 / 前端 mock / 已接后端；验证状态：未验证 / 局部验证 / 已按验收条件验证。源码存在、测试通过、用户验收分别记录。
- 新设计标明取代旧设计的具体部分，旧背景保留。日期更晚不自动获得优先权。
- 文档与代码不符时核查并登记差异，不默认任一方正确。归档不等于已验收，计划预期输出不等于实际测试结果。
- 网络或权限不可用时注明阻塞，不能把旧快照当最新进度。

## Git 与迁移

文档和 Issue 模板随代码管理；本地修改、提交、推送分别说明，不能混为一谈。问题和需求使用 GitHub `#编号`，仓库不复制讨论、处理状态或维护编号映射正文。

未提交文档以仓库路径标识，不伪造远端文件链接。
