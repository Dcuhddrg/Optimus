# Auth RBAC Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first-version Optimus login, LDAP user sync, JWT authentication, RBAC authorization, and System admin UI described in `docs/superpowers/specs/2026-05-07-auth-rbac-design.md`.

**Architecture:** Keep the existing Gin layering and add focused `system` packages for auth, user, role, permission, LDAP, and audit behavior. The backend owns seeded permission metadata and default-deny API authorization; the frontend consumes `/system/auth/me` to protect routes and filter navigation.

**Tech Stack:** Go 1.23, Gin, GORM/MySQL, jwt/v5, Casbin-compatible RBAC, bcrypt, `github.com/go-ldap/ldap/v3`, hand-written fake interfaces, React 18, React Router, TypeScript, CSS Modules.

---

## Scope Notes

- This is a single feature plan because auth, users, RBAC, LDAP, audit, and the frontend shell must work together to produce a testable login/admin loop.
- Do not create arbitrary local password users. Only the seeded `admin` account uses local password auth.
- Do not add online create/delete for menu/API permission metadata. Permission rows are seeded by backend code.
- Do not add a frontend UI component library.
- Backend LDAP requires adding `github.com/go-ldap/ldap/v3` for real LDAP search and bind behavior. This is the only planned new runtime dependency in this feature.
- Keep existing dirty files unrelated to this plan untouched: `deploy/docker-compose/.env.example`, `deploy/docker-compose/Dockerfile.frontend`, and `.superpowers/brainstorm/**`.
